### 実行環境に関する重要な注意（検証方法の差異）
- **dev serverではなく、本番ビルド（`next build`＋`next start`）で検証した。** Windowsのメモリ（物理＋コミット）が逼迫し、dev server（Turbopack）が`memory allocation of 16777216 bytes failed`、webpackモードも`Manifest file is empty`で停止したため。ビルド自体は成功している。
- そのため**Reactのハイドレーション警告は、開発ビルドの警告文ではなく、本番の「Minified React error」として検出される**。`hydrat`を含むコンソール出力と、ページ例外を監視したが、0件だった（開発ビルドでの再確認は未実施）。
- 発行直後のセッショントークンが「JWT issued at future」で弾かれることがあり、検証スクリプト側で発行後7秒待つ対処を入れた（ローカルDockerとホストの時計のずれ。アプリの不具合ではない）。

## 4. 気づいた点（不具合とは言えないが、改善の余地があるもの）

1. **資料の重複アップロード（B3）**：同じ資料を再アップロードすると同名の別行として登録される。重複チェックは無い（仕様の記載なし）。AI素案の生成で資料が二重に渡され、規約49の「重複で抽出が不安定」の原因になりうる。
2. **顧客の作成はadmin専用（A1a）**：pmは顧客を作れず、案件作成画面で既存の顧客を選ぶだけ。シナリオは「pmが顧客を作成」だが、期待値はdocsに記載が無く不明。
3. **再生成で、確定済みと同内容のAI素案が重複して出る（C7b）**：確定した項目は保持される一方、同じ内容のAI素案が新しく追加され、確定済み項目と同名のものが並ぶ。
4. **KPIのAI候補を1件だけ採用すると、残りの候補が消える（C2h）**：新ノードが選択され候補パネルが再マウントされるため。「すべて採用」なら問題ない。
5. **「PowerPoint（詳細・全章）」という出力は無い（F1b）**：出力メニューはWordとPowerPoint（サマリー）のみ。実際のPPTXには案件概要と全章のスライドが含まれる。シナリオ（サマリー／詳細の2種類）と実装が異なる。
6. **Wordに不採用（rejected）の項目も出力される（F2-word）**：仕様の記載がなく、不採用項目を出力に含めるかは要判断。
7. **曖昧表現の辞書チェックは「適宜」を検出するが「できるだけ」は検出しない（C-other）**：辞書の網羅性。生成直後から「素案生成時」の曖昧フラグが多くの項目に付き、サイドバーの⚠が常態化している（⚠2〜3件が大半の章に出る）。
8. **パートナーの数値は、7章（RLSで非公開）が集計から落ち、他ロールと一致しない（G2b）**：ヘッダー・7章カード（「未着手 0/0」と表示され、非公開であることが分からない）。情報の漏れは無いが、混乱しうる。7章をパートナーに隠す仕様自体がdocsに明記されていない。
9. **member/partnerに権限の無い操作のUIが出る（G1b・G1-create-note）**：メンバー追加フォーム、「+ 新規案件」。実行はサーバー/RLSで拒否される。
10. **項目編集の保存が通信断で失敗したとき、保存されていない値が入力欄に残る（I1-edit）**：トーストは日本語で出るが、画面の値は元に戻らない（規約58の観点）。
11. **整合性チェックの未反映ステップ（E3）**：業務フローのTo-Be新設ステップ6件が「9章に未反映」と表示された（9章の機能名と業務フローのステップ名の照合が名称一致のため）。
12. **画面遷移図の「すべて採用」直後のトースト**：検証スクリプトでは文言を取得できなかった（表示が短い、または表示されていない可能性。画面操作としては採用結果は正しく反映された）。
13. **整合性チェック（孤立要件）は、AI生成した項目が出典（item_sources）を持つため0件で通る**：出典の有無だけを見るため、出典の正しさまでは検証されない。

## 5. 手動確認が必要な項目

ローカルでは検証できないため、ユーザーがStagingで確認する。

- **Googleログイン**：自社ドメインの初回自動登録、再ログイン、他ドメインの未登録の拒否、他ドメインの事前登録済みの許可。
- **Vercel上のAI生成の所要時間**：ローカルで測った最長は**23秒**（業務フローAs-Isの生成）。章ごとの素案生成は10〜19秒、画面遷移図の差分提案19秒、KPI素案11秒、AI曖昧判定（1項目）数秒。**一括生成（1章ずつ順次）は10章で131秒**かかるため、1回のServer Actionではなくクライアントから章ごとに呼ぶ現行方式のまま、各呼び出しがプランの関数実行時間の上限（例：10秒／60秒）に収まるかを確認する。長い資料（約3MB）の場合は更に延びうる。
- **Staging上でのファイルアップロード**：数MBのPDF・PPTX（ローカルでは合成ファイル3.0MB・3.1MBで成功）。Storageの上限・CORS・Vercelのボディ上限（直接アップロード方式のため影響は小さい想定）。
- **パートナー権限での案件トップ**（Stagingのテストユーザー）：7章が集計から落ちる挙動（G2b）を含む。
- 追加：**開発ビルドでのハイドレーション警告の再確認**（本検証は本番ビルドで実施したため）。
- 追加：**案件削除後のStorage残存（B-K1）**：Stagingで、メンバーではない管理者が削除した場合の挙動。
