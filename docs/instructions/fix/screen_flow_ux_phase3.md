# 指示書：画面遷移図UX改善 フェーズ3（AI素案の差分提案）

## 目的

画面遷移図のAI素案を、現状の「ノードが0件のときだけ全件を一括生成する」方式から、**既存の図と9章の機能要件を入力に、追加すべき画面と遷移だけを破線で提案し、個別または一括で採用・見送りできる**方式に置き換える（ハンドオフの「AI素案（差分で提案）」）。

**対象外**：キーボード操作・Ctrl/⌘+ホイールズーム・スペース+ドラッグのパン・各操作の失敗時ロールバックの総点検・視覚仕上げ（フェーズ4）。

## 重要な設計判断

### 1. 提案は専用テーブルに保存する（KPI・非機能要件の候補パネルとは方針が異なる）
KPI画面・非機能要件画面の候補は、右パネル内の一時的な候補リストなので「DBに保存しない」簡略化を採った。今回の提案は**キャンバス上に破線で描画され、ページを離れても残り、見送った提案は再提案されない**ことをハンドオフが求めている（`AiSuggestion`はサーバ側データ）。そのため、提案専用のテーブルを1つ追加する。`flow_nodes`/`flow_edges`に「提案中」の行を混ぜる方式は取らない（警告・確定件数・Word/Excel出力・既存の`existingCount`ガード等、`flow_nodes`を読むすべての箇所で提案行を除外する必要が生じ、取りこぼしの危険が大きいため。規約36・37）。

### 2. 差分のみを提案し、既存は変更しない
モデルが返すのは「追加すべきノード」と「追加すべき遷移」だけ。既存のノード・遷移の変更・削除は提案させない。

### 3. 採用のルール
- ノード提案は、採用すると実ノードを作る。作られたノードの`status`は`ai_draft`（表示「下書き」）。9章項目への紐付けが提案に含まれていれば、同時に紐付ける
- 遷移提案は、**遷移元・遷移先の両方が実ノードになっているときだけ採用できる**。端点が未採用のノード提案の場合は「先に画面を採用してください」と表示し、採用ボタンを無効にする（ハンドオフの「AI提案中のノードは確定不可」と同じ考え方）
- ノード提案を**見送る**と、そのノードに接続する未対応の遷移提案もあわせて見送り扱いにする（ハンドオフ：ノードを見送ると、そのノードに接続するAI遷移も消える）
- 「すべて採用」は、**ノード提案を先に、遷移提案を後に**処理する。個別の失敗（9章項目が既に別画面に紐付いた、遷移元が確定済みになった等）で全体を止めず、「N件を採用しました（M件は採用できませんでした）」と集計して返す
- **確定済みノードを遷移元とする遷移提案は、生成時に作らない**。それでも採用時には既存の`addScreenTransition`と同じロック判定（遷移元が`isItemLocked`なら拒否、フェーズ2）を必ず通す（規約33）

### 4. 採用・見送りで楽観的更新はしない
提案の一覧と実ノード・実遷移は同じサーバー再取得で同時に切り替わるため、採用直後に破線の提案が消えて実ノードが現れるまで、ちらつきは起きない。ボタンを操作中は無効化して連打を防ぐ。上書き値（規約59）の仕組みは使わない。

### 5. 旧一括生成は置き換える
`generateScreenTransitionDraft`（ノード0件時のみ・全置換の一括生成）は、このAI素案に統合して**撤去する**。ノードが0件の図でも、9章の画面情報から画面の提案が出せるため、機能は失われない。撤去前に呼び出し箇所・ボタン・関連文言をgrepで洗い出すこと（規約36）。旧プロンプト（`extract_screen_transitions`）の行はDBに残してよい（削除しない）。

## 前提確認

- フェーズ2（Staging反映済み・回帰確認済み）が完了していること。特に、フェーズ2で確認が残っていた「9章紐付けの変更・解除」「画面の追加」「警告表示」が正しく動くこと
- ハンドオフの`画面遷移図 7a 高精度デザイン.dc.html`で`aiSuggest()`と、提案の採用・見送りの挙動、提案ノード/提案遷移の見た目（破線・タグ・右パネルの表示）を実際に操作して確認すること。**本指示書の要約よりHTMLの実際の挙動を優先する**
- 実際に使われているGeminiのモデル名、`callGeminiSafely`・`getActivePrompt`・`ai_interactions`への記録の書き方を、既存のAI呼び出し（`suggestKpiCandidates`・`suggestNonfunctionalCandidates`）で確認してから合わせること

## Step 1: 提案テーブルを追加する

マイグレーションで`screen_flow_suggestions`を作成する。

- `id`（uuid・主キー）、`project_id`（`projects(id)`への外部キー、**`ON DELETE CASCADE`**。案件削除で提案も消えること。規約48）
- `kind`（`'node'`／`'transition'`）
- `payload`（jsonb）：下記の形
- `why`（text・必須）：根拠1文
- `state`（`'open'`／`'adopted'`／`'rejected'`、既定`'open'`）
- `result_id`（uuid・null可）：採用で作られた実ノードまたは実遷移のid
- `created_at`

`payload`の形：

- ノード提案：`{ name, function_item_id | null, x, y }`
- 遷移提案：`{ from: { ref: 'node' | 'suggestion', id, name }, to: { ref: 'node' | 'suggestion', id, name }, label }`
  - `ref: 'node'`は既存の実ノードのid、`ref: 'suggestion'`は同じ生成で作られたノード提案のid
  - `name`は表示と、見送りの記録による再提案の抑止（名前による照合）に使う

RLS・GRANTは、案件メンバーのみが読み書きできるよう、既存の案件配下テーブルと同じ方式で設定する（`CREATE TABLE`＋`ENABLE RLS`＋SELECT/INSERT/UPDATE/DELETEの各ポリシー＋`GRANT`。規約12・16）。`tenant_id`列の扱いは、`flow_nodes`など近いテーブルの実際の構成に合わせる。`docs/02_architecture.md`にテーブル定義を追記すること。

## Step 2: 提案の正規化・配置ロジックを純粋関数で実装する

`src/lib/screen-flow/suggestions.ts`（通常モジュール、DB非依存）に実装する。**モデルの生の出力を検証・整形する処理は、Geminiを呼ばずに単体で検証できるよう、必ず純粋関数にする。**

`normalizeSuggestions(raw, context)`の仕様：

- 入力の`raw`は、モデルが返したJSONを`zod`で検証したもの。`context`は、実ノード（コード`S-NN`・名前・紐付け・状態）、実遷移、9章の画面情報つき項目（コード`F-NN`。画面イメージ・xlsx出力と同じ判定と同じ採番関数を共有すること）、見送り済みの提案
- モデルへは**uuidを渡さず**、実ノードは`S-NN`、9章項目は`F-NN`、新規ノードは`N1`、`N2`…という短い参照名で渡し、返ってきた参照を実idに戻す（ハルシネーションと取り違えの防止）
- 次のものは**黙って捨てる**：
  - 未知の参照を含む遷移
  - 自己ループ
  - 実在する遷移と同じ`(from,to)`のもの、提案同士で重複するもの
  - 実ノードまたは他の提案と同名のノード提案
  - 見送り済みのノード名、見送り済みの`(from名,to名)`の遷移
  - 確定済みノードを遷移元とする遷移
  - すでに別ノードに紐付いている9章項目を指すノード提案（存在しない`F-NN`を指している場合は、紐付けなしのノード提案として扱う）
- 件数の上限をかける（既定：ノード8件・遷移20件。超過分は切り捨て）
- 遷移提案の`from`/`to`は、実ノードなら`{ ref: 'node', id }`、提案ノードなら`{ ref: 'suggestion', key }`に正規化する（保存時にidへ変換）

`placeProposedNodes(realNodes, proposals)`の仕様：

- 提案ノードに座標を割り当てる。接続する実ノードがあればその右隣（`layout.ts`の列間隔・行間隔の定数を共用）、無ければ既存ノードの外接矩形の下に置く
- 実ノード・他の提案ノードと矩形が重ならないこと（重なる場合は行を下にずらして探索する）
- 座標は決定的に求めること

## Step 3: プロンプトを登録する

マイグレーションで`suggest_screen_flow_diff`（`is_active`・バージョン管理は既存の登録方式に合わせる）を登録する。要点：

- 役割：画面遷移図の**差分提案**。既存のノード・遷移は変更も削除もしない。追加すべきものだけを返す
- 用語の定義（規約57）：「画面」＝利用者が操作する1つの画面、「遷移」＝ある画面から別の画面への移動（操作名つき）。**条件分岐は扱わない**。1つの画面から複数の遷移が並列に存在してよい
- 入力：既存の画面一覧（`S-NN`・名前・紐付け先の`F-NN`）、既存の遷移、9章の画面情報つき項目（`F-NN`・機能名・画面パターン・表示項目・操作・内容。**全件を渡す**。長くなる場合のみ、1項目あたりの文字数を制限し、項目自体を黙って落とさない。規約56）、見送り済みの提案（出さないこと）
- 提案の観点：9章の画面でまだ図に無いもの、9章の「操作」から読み取れる画面間の移動、一覧→詳細→編集→削除確認のような一般的な画面遷移
- すべての提案に**根拠を1文**で付ける（どの9章項目・どの既存画面から導いたかが分かること）。9章に根拠が無い一般論は、そう分かる書き方にする
- 出力は次のJSONのみ：`{"nodes":[{"key":"N1","name":"…","function":"F-04"|null,"why":"…"}],"transitions":[{"from":"S-01"|"N1","to":"S-02"|"N1","label":"…","why":"…"}]}`

呼び出しは`responseMimeType: "application/json"`・低い`temperature`（0.2前後。規約49）。

## Step 4: Server Actionを実装する

`src/actions/`に追加する（実際のシグネチャ・戻り値は既存のアクションに合わせる。規約50。エラーは`UserFacingError`＋`errorMessage()`。規約43）。

- `generateScreenFlowSuggestions(projectId)`
  - 実ノード・実遷移・9章項目・見送り済みの提案を取得し、Geminiを呼び、`normalizeSuggestions`→`placeProposedNodes`を通して保存する
  - **保存の前に、同じ案件の`state='open'`の提案を削除する**（未対応の提案は再生成で置き換える。`adopted`／`rejected`は履歴として残す）
  - 実ノードも9章の画面情報つき項目も無いときは、「画面情報を持つ9章の機能要件がありません」とエラーにする
  - `ai_interactions`に、入力の件数・出力の件数・検証で捨てた件数を記録する
- `adoptScreenSuggestion(suggestionId, projectId)`
  - ノード提案：既存の`addScreenNode`と**同じ作成処理を共用**する（画面ID`S-NN`の採番・9章紐付けの一意性チェックを重複実装しない）。`status: 'ai_draft'`。作成したidを`result_id`に保存し、`state='adopted'`にして、作成したidを返す
  - 遷移提案：端点を解決する（`ref:'suggestion'`なら、その提案が`adopted`のときの`result_id`を使う。未採用なら`UserFacingError`「先に画面を採用してください」）。既存の`addScreenTransition`と同じ検証（自己ループ・重複・遷移元のロック）を通して作成する
  - 更新件数を確認する（規約47）
- `rejectScreenSuggestion(suggestionId, projectId)`：`state='rejected'`。ノード提案の場合は、そのノードを端点とする`open`の遷移提案もあわせて`rejected`にする
- `adoptAllScreenSuggestions(projectId)`／`rejectAllScreenSuggestions(projectId)`：上記のルールどおり（ノード→遷移の順。個別の失敗は集計して返す）
- 提案の取得は、表示用に`state='open'`のものを返す。**端点が実ノードを指しているのに、そのノードが既に削除されている遷移提案は、取得時に除外する**

## Step 5: キャンバスに提案を描画する

- ヘッダーの「AI素案（差分で提案）」ボタンを常に表示する（旧「0件時のみ」の一括生成ボタンは撤去）。生成中はボタン内に「生成中…」を表示して無効化する（既存のAI生成ボタンの表現に合わせる）
- 提案がある間（`open`が1件以上）、ヘッダーに**AI提案バー**を表示する：破線の枠に「AI提案 N 件」＋「すべて採用」（primary小）＋「すべて見送り」（白小）
- 提案ノード：背景はわずかに淡く、**破線の枠**、「AI提案」タグ。ポートは出さない。**ドラッグ移動はできない**（採用後に通常のノードとして移動できる）
- 提案遷移：破線（`5 4`）・淡い色、ラベルも破線の枠。`geom()`を再利用し、提案ノードも端点として扱う
- ステージの論理サイズは、実ノードに加えて**提案ノードも含めた外接矩形**から算出する（提案ノードが見えない位置に置かれないように）
- **警告・サマリーピル・「確定 k/N」・「9章にあって図にない画面」の計算には、提案を一切含めない**（`derive.ts`には実ノード・実遷移だけを渡す）

## Step 6: 右パネルに提案のモードを追加する

- 提案ノードを選択：「AI提案」ピル、画面名（読み取り専用）、9章の紐付け先（あれば機能名と画面イメージ。既存の画面イメージ縮小表示を再利用）、**根拠**、「採用」「見送り」。確定ボタンは出さない
- 提案遷移を選択：遷移元 → 遷移先、操作名（読み取り専用）、**根拠**、「採用」「見送り」。端点が未採用の提案ノードのときは「先に画面を採用してください」と表示し、採用を無効にする
- 画面ノード選択時の**遷移先一覧**に、そのノードを遷移元とする提案遷移を破線の行として表示し、「採用」「見送り」を付ける
- 採用したら、作られた実ノード（または実遷移）を選択状態にする。**作成したidが再取得データに現れるまで選択を解除しないこと**（フェーズ2の遷移作成と同じ扱い）
- 選択していた提案が見送られた・置き換えられた場合は、選択を解除する
- 入力欄の`key`はidだけでなく値も含める（規約58）

## Step 7: 旧一括生成を撤去する

`generateScreenTransitionDraft`と、その呼び出し元（ボタン・フォーム）、不要になった関連文言をgrepで洗い出して撤去する。参照が残っていないことを確認する（規約36）。

## Step 8: 動作確認

**Geminiの日次クォータが限られている（無料枠で1日20回程度）ため、実際のGemini呼び出しは合計6回以内に収めること。** 検証の大半は、Geminiを呼ばない純粋関数の検証と、DBに直接入れた提案データで行う。

**純粋関数（Gemini不要）**
1. `normalizeSuggestions`に、次を含む偽の出力を与えて期待どおり処理されることを確認する：未知の参照、自己ループ、既存と重複する遷移、提案同士の重複、同名のノード、見送り済みの名前・組、確定済みノードからの遷移、紐付け済みの9章項目を指すノード提案、上限超過
2. `placeProposedNodes`で、提案ノードが実ノード・他の提案と重ならず、毎回同じ座標になることを確認する

**実際の生成（Gemini 1〜2回）**
3. 9章に画面情報つき項目が4件ほどあり、図に画面が1〜2件ある案件で生成し、破線の提案ノード・提案遷移が描画され、AI提案バーの件数が正しいことを確認する。リロードしても提案が残ることを確認する
4. 提案に根拠が付き、右パネルに表示されることを確認する
5. ノードが0件の案件でも、9章の画面から画面の提案が出ることを確認する

**採用・見送り（DB上の提案データで確認してよい）**
6. ノード提案を採用すると実ノード（`ai_draft`・「下書き」）になり、9章への紐付けも設定され、選択状態になることを確認する。破線の提案が消えて実ノードが現れるまで、ちらつきが無いことを確認する
7. 端点が未採用の提案ノードである遷移提案は採用できない（無効表示）。ノードを採用した後は採用できることを確認する
8. ノード提案を見送ると、そのノードに接続する遷移提案も消えることを確認する
9. 「すべて採用」でノード→遷移の順に処理され、個別の失敗があっても集計が表示されることを確認する（例：採用前に9章項目を別画面に紐付けて失敗を起こす）
10. 「すべて見送り」で、未対応の提案がすべて消えることを確認する

**再生成・再提案の抑止（Gemini 1〜2回）**
11. 提案を一部見送ってから再生成し、見送った提案が再び出ないこと、未対応だった提案は新しい結果に置き換わること、採用済みの実ノードは影響を受けないことを確認する

**ロックとサーバー側の拒否**
12. 画面を確定済みにし、そのノードを遷移元とする遷移提案が生成されないことを確認する。さらに、確定済みノードを遷移元とする遷移提案を**DBに直接入れて**採用を試み、Server Actionが拒否することを確認する（規約33）

**整合性**
13. 提案がある状態で、警告・サマリーピル・「確定 k/N」・「9章にあって図にない画面」が、提案を含まない値のままであることを確認する。Word/PowerPoint/Excelの出力、確定判定ダッシュボードが、提案の有無で変わらないことを確認する
14. 案件を削除すると、その案件の提案行も消えることを確認する（規約48）。案件メンバーではないユーザーが提案を読めない・更新できないことを、更新件数まで含めて確認する（規約47）
15. 提案が指す実ノードを削除すると、その遷移提案が表示されなくなることを確認する

**回帰**
16. フェーズ1・2の機能（ドラッグ移動、ズーム、ポートからの遷移作成、自動で整列、確定ワークフロー、9章への紐付けの変更・解除、画面の追加・削除、警告表示）に回帰が無いことを確認する。**9章への紐付けの変更・解除、画面の追加、警告表示は、前回通していないため必ず通す**

## やってはいけないこと

- `flow_nodes`・`flow_edges`に「提案中」の行を混ぜること（提案は専用テーブルに保存する）
- モデルにuuidを渡すこと（`S-NN`・`F-NN`・`N1`の短い参照名を使い、サーバー側で実idに戻す）
- 生成のたびに、決定済み（`adopted`／`rejected`）の提案を消すこと
- 採用・見送りに楽観的更新（上書き値）を持ち込むこと
- 画面ID採番・9章紐付けの一意性チェックを、採用処理で別に実装し直すこと（`addScreenNode`の処理を共用する）
- 実際のGemini呼び出しを検証のたびに繰り返すこと（純粋関数とDB上のデータで済む項目は、そちらで検証する）
- キーボード操作・パン・ホイールズームを本フェーズで実装しないこと
