# 指示書：Server Actionのエラーを「戻り値」で利用者に届ける（本番ビルドで文言が消える問題の修正）

## 目的

本番ビルドでは、Server Actionが`throw`した例外のメッセージが、利用者に届く前に消える（実測済み）。

- `<form action>`に渡したActionが投げると、汎用のエラー画面になる
- クライアントの`try/catch`で受けると、`An error occurred in the Server Components render…`という**英語の長文**がトーストに出る（日本語の理由は届かない）
- 戻り値で返す形（`{ error }`）だけが、本番でも文言が届く

利用者に理由を見せる必要がある失敗（ロック中の拒否・権限・重複・入力不正・対象なし）を、**戻り値で返す形に統一**する。

## 決定事項

**方式**：`ActionResult`を戻り値にし、`throw`した例外を捕まえて結果に変換するラッパー`safeAction()`を導入する（実測報告の案1）。`digest`から文言を引く方式（案2）は採らない。

**範囲**：次の**79件**をすべて変換する。ただし、**段階に分けて進め、各段階で止めて報告する**。

| 区分 | 件数 | 扱い |
|---|---|---|
| `<form action>`に直接渡しているもの | 20 | 変換する（`useActionState`の形に寄せる） |
| クライアントの`try/catch`で呼ぶもの | 59 | 変換する |
| 既に戻り値で返しているもの（`generateDraft`等） | 13 | **変更しない**（動いている） |
| ページ描画中に呼ぶ読み取り系 | 32 | **変更しない**（`throw`のまま。失敗は`error.tsx`が受ける） |
| 未使用 | 3 | 触らない |

## 設計

### 型とラッパー（`src/lib/action-result.ts`等）
```ts
export type ActionResult<T = void> =
  | { ok: true; data: T }
  | { ok: false; error: string };
```
- `safeAction(fn)`：`fn`を呼び、成功なら`{ ok: true, data }`を返す。失敗時の扱いは次のとおり。
  - **`UserFacingError`** → `{ ok: false, error: その文言 }`
  - **`redirect()`・`notFound()`などの、Next.jsの制御用の例外は、必ず再`throw`する**（捕まえて握りつぶすとリダイレクトが壊れる）。使っているNext.jsのバージョンの、制御用エラーを再throwする仕組み（`unstable_rethrow`等）を、公式ドキュメントで確認して使う
  - **それ以外の予期しない例外** → サーバーログに記録し（アクション名と、元のメッセージ・スタック）、`errorMessage()`の既知パターン辞書で日本語に変換できればそれを、できなければ「処理に失敗しました。時間をおいて、もう一度お試しください。」を返す
  - **開発と本番で挙動を変えない**（今回の問題の根は、dev serverと本番ビルドの差だった）
- `<form action>`用には、`useActionState`の形（`(prevState, formData) => Promise<{ error: string | null }>`。規約50）で同じ変換を行うラッパーを用意する。成功時に`redirect()`していたものは、そのまま`redirect()`でよい（制御用の例外として再throwされる）
- 戻り値は、**直列化できる値だけ**にする（クラスのインスタンス等を返さない）。これまで`createKpiNode`のようにidを返していたものは、`data`に入れる

### クライアント側
- 呼び出し側は、`result.ok`を見て、`false`ならトーストで`result.error`を表示する。**`try/catch`は残す**（通信エラー等、クライアントで発生する例外のため。`errorMessage()`で日本語化する。規約43・44）。小さな共通ヘルパーを用意して、同じ書き方の重複を避けてよい
- 楽観的に画面を更新している操作（ドラッグ・並べ替え・自動整列）は、`ok: false`のときに上書きを外して元へ戻す（これまでの失敗時の挙動と同じ）
- **二重のトースト**（実測のB2：確定ボタンでトーストが2つ出る）が出ないこと

### 英語メッセージの日本語化（`errorMessage()`）
実測のDで、資料の再分類が「Object not found」（Storageの英語）をそのまま表示した。`errorMessage()`に、**既知のSupabase・Storage・PostgRESTのメッセージの対応表**を持たせる（例：`Object not found`、`Bucket not found`、`The resource already exists`、`duplicate key value violates unique constraint`、`new row violates row-level security policy`、`Payload too large`など）。対応表に無い英語は、そのまま表示せず「処理に失敗しました…」とし、元のメッセージはサーバーログに残す。

### `error.tsx`
案件配下の`error.tsx`に、**エラーID（`error.digest`）を小さく表示する**（サーバーのログと突き合わせて原因を追えるように）。メッセージの出し分けは、現状のままでよい。

### 画面遷移図「すべて採用」
個別の失敗理由を`catch {}`で捨てている。`failed`に理由を持たせて返し、トーストに「N件を採用しました。M件は採用できませんでした（〇〇：2件、△△：1件）」の形で集計して表示する。

## 前提確認

- 実測・洗い出しの報告（`server-action-error-paths.md`）を、この指示書の分類の根拠として使う。**変換の対象は、実際のコードで再度grepして確認する**（記憶・報告書の件数に頼らない）
- 検証は**すべて本番ビルド（`next build`＋`next start`）で行う**。dev serverでは文言が届くため、devだけでは検証にならない

| 5 | 再発防止と最終確認：下記 |

### 段階5：再発防止と最終確認
- 「クライアントから呼ばれるServer Actionが、`safeAction`（またはフォーム用ラッパー）を通っていること」を確認する簡易なチェック（スクリプト等。`UserFacingError`を`throw`しているのに、ラッパーを通っていない書き込み系のアクションを列挙する）を作り、`package.json`にコマンドとして登録する。読み取り系は対象外
- 全アクションの分類表（変換済み／戻り値方式／読み取り系）を、`docs/`に残す
- 全画面の主要な失敗経路を、本番ビルドで再確認する

## 各段階の共通の検証

- 変換した各アクションについて、**成功の経路と、失敗の経路を1つ以上**、本番ビルドで画面から実行し、日本語の文言がトースト（またはインライン）に出ることを確認する。**同じ操作のdev serverでの文言と一致する**こと
- `<form action>`の失敗が、汎用のエラー画面ではなく、**フォーム内のインラインのエラー**として表示される。入力した内容が消えない
- 成功時の挙動（リダイレクト、`revalidatePath`による再取得、戻り値のid等）が、これまでと変わらない
- 通信を中断した場合のトースト（`errorMessage()`による日本語）が、これまでどおり出る
- 楽観的に更新している操作で、失敗時に元へ戻る
- 型チェックがエラー0件（`any`で逃げない）。ESLintもエラー0件

## やってはいけないこと

- `digest`から文言を引く仕組み（案2）を作ること
- 開発と本番で、挙動や文言を変えること
- `redirect()`・`notFound()`の例外を握りつぶすこと
- 呼び出し側の修正を伴わずに、戻り値の型だけを変えること（型エラーで気づけるが、`any`・`@ts-ignore`で逃げない）
- ページ描画中に呼ぶ読み取り系の`throw`を、変換すること
- 日本語の文言を、英語の漏れの修正以外の理由で書き換えること
- 複数の段階を、1つのコミットにまとめること
