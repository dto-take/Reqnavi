# 指示書：要件定義画面UX改善 フェーズ1（データモデル準備・カード型レンダリングへの置き換え）

## 目的

添付のデザインハンドオフ（`design_handoff_requirements_screen/README.md`）に基づき、テンプレートA/B/C（5〜9,11〜14章、共通の`RequirementTable`）の表示を、横長テーブルから「1項目=1カード」の形式に置き換える。

**本フェーズの対象は「カード化」のみ**とし、グループ化（フェーズ2）・一括操作（フェーズ3）・フィルタ（フェーズ4）・曖昧表現のインライン表示等の視覚的仕上げ（フェーズ5）は対象外とする。既存の全操作（確定・リスク許容で確定・不採用にする・削除・AI提案・ドラッグ並び替え・内容編集）は、カード形式の中に過不足なく移植する。

## 重要な方針：デザイントークンの扱い

デザインハンドオフは独自の配色・書体（Shippori Mincho・IBM Plex Mono・琥珀/赤茶系の警告色）を提案しているが、**ReqNaviは既存のデザインシステム（深緑系ブランドカラー・Inter一本化、規約38〜41）を優先する**。README自身も「既存プロダクトのデザインシステムが優先」と明記している。

- 緑（primary）・警告色（曖昧表現）・注意色（要レビュー）の**役割**はそのまま踏襲する（緑=確定/primary、琥珀系=要レビュー、赤茶系=曖昧表現という対応関係）が、**実際の値はReqNaviの既存トークン（`--brand`・`--status-*`）にマップする**
- 書体の使い分け（見出しに明朝、数値にモノスペース）という考え方だけ踏襲したい場合は判断を委ねるが、必須ではない。Inter一本化を崩してまで新フォントを追加する必要は無い
- カードの余白・角丸・シャドウ等の具体的な数値は、ハンドオフの値を参考にしつつ、既存の共通コンポーネントとの一貫性を優先してよい

## Step 1: 最終更新者列を追加

```bash
supabase migration new add_requirement_item_updated_by
```

```sql
alter table requirement_items add column if not exists updated_by uuid references auth.users(id);

create or replace function set_requirement_item_updated_by()
returns trigger
language plpgsql
security definer
set search_path = ''
as $$
begin
  new.updated_by := auth.uid();
  return new;
end;
$$;

create trigger set_updated_by
  before update on requirement_items
  for each row execute function set_requirement_item_updated_by();
```

**注意**：全てのUPDATE経路を個別に修正する必要が無いよう、トリガーで自動的に記録する設計にしている（規約39と同様の「共通処理はトリガーに寄せる」考え方）。

`listRequirementItems`（`src/actions/requirement-items.ts`）の取得列に`updated_by`を追加し、`user_profiles`と結合して更新者名を取得できるようにする（既存の`item_sources`埋め込みJOINと同様の実装パターン）。

## Step 2: カード型コンポーネントを作成

新規ファイル `src/components/domain/requirement-table/RequirementCard.tsx`。

デザインハンドオフの「項目カード（展開形）」節・「項目カード（1行形）」節の構成を移植する。

- **展開形（既定）**：バッジ行（ステータス・曖昧表現件数・AI素案・出典件数・更新者/時刻）／本文（`content`の主要テキスト列）／項目サマリ（残りの列を`listColumnDefs`から動的に取得し、値があれば表示、無ければ「＋ 未入力」のクリック可能なプレースホルダにする）／アクション行（確定・開いて編集相当・⋯メニュー）
- **1行形（確定済み・不採用等のロック状態）**：本文の要約＋入力充足率＋「開く」ボタンのみの簡略表示。展開形に戻すトグルを用意する

**注意**：「SOLUTION / KPI / MERIT・DEMERIT」はハンドオフのサンプル（テンプレートA固有の列名）であり、実際にはテンプレートB・Cで列名が異なる。ハードコードせず、既存の`listColumnDefs(templateType, chapterNo)`で取得した列定義を汎用的にループ表示すること。

「⋯」メニューには、既存の「リスク許容で確定」「不採用にする」「この項目を確認」「削除」を移植する（開閉可能なドロップダウンメニューコンポーネントを新規作成し、他の画面でも再利用できる形にしてよい）。

## Step 3: 既存のRequirementTableを置き換え

`src/components/domain/requirement-table/RequirementTable.tsx`のテーブル描画部分を、`RequirementCard`のリスト表示に置き換える。

- ドラッグ&ドロップによる並び替え（既存機能）は、カード全体を対象にした並び替えとして維持する（ドラッグハンドル`⠿`をカード左端に配置する）
- 既存の空状態（0件時の案内メッセージ）はそのまま維持する

## Step 4: 動作確認

1. 複数の項目がある章（例：8章・9章）を開き、テーブルではなくカード形式で表示されることを確認する
2. 未入力の列に「＋ 未入力」が表示され、クリックすると入力できることを確認する
3. 確定済み・不採用の項目が1行形（簡略表示）になり、「開く」で詳細が展開されることを確認する
4. 「⋯」メニューから、リスク許容で確定・不採用にする・削除がこれまで通り実行できることを確認する
5. ドラッグ&ドロップでのカード並び替えが引き続き機能することを確認する
6. AI素案生成・曖昧表現チェックが引き続き正しく機能することを確認する
7. カードのバッジ行に「更新○分前・○○」が表示され、実際に編集した直後は編集者名が反映されることを確認する
8. テンプレートA・B・Cそれぞれの章で、項目サマリの列名・値が正しく表示されることを確認する

## やってはいけないこと

- グループ見出し・一括操作バー・フィルタチップを本フェーズで実装しない（フェーズ2〜4の対象）
- テンプレートA固有の列名（SOLUTION・KPI等）をハードコードしない
- 既存の操作のいずれかを、カード化の際に欠落させない
