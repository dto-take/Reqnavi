# 指示書：画面遷移図UX改善 フェーズ2（ポートからの遷移作成・自動整列・ズーム・確定ワークフロー）

## 目的

フェーズ1で作ったキャンバス＋右パネルに、次の4点を追加する。

1. ノード右端のポート（●）から別ノードへドラッグして遷移を作成する
2. 「自動で整列」（BFSによる層分け配置）
3. ズーム（ツールバー操作。50〜160%）
4. 画面ノード単位の確定ワークフロー（「この画面を確定」・確定後の編集ロック）

**対象外**：AI素案の差分提案（フェーズ3）、キーボード操作・Ctrl/⌘+ホイールズーム・スペース+ドラッグのパン・各操作の失敗時ロールバックの総点検・視覚仕上げ（フェーズ4）。

## 重要な設計判断

### 1. ステータスは新しい語彙を作らない
フェーズ1の方針どおり、`flow_nodes.status`は`ai_draft`（表示「下書き」）／`se_reviewing`（「要レビュー」）／`confirmed`（「確定済」）を使い、ロック判定は既存の`isItemLocked`（`src/lib/item-lock.ts`）をそのまま使う。**新しいマイグレーションは不要**の想定（必要になった場合のみ追加する）。

### 2. 確定済みノードのロック範囲（本指示書で決める）
ハンドオフにはロック範囲の記述が無いため、次のとおりとする。KPI・非機能要件と同じく「確定したら中身は変えられない」を基本にしつつ、**配置はコンテンツではないため対象外**にする。

| 操作 | 確定済みノード |
|---|---|
| 画面名の変更 | 不可 |
| 9章への紐付けの変更・解除 | 不可 |
| そのノードを**遷移元とする**遷移の追加・削除・操作名の編集（戻りの遷移の追加を含む） | 不可 |
| ポートからのドラッグ（そのノードを遷移元にする） | 不可 |
| ドラッグでの位置移動・「自動で整列」による再配置 | **可**（レイアウトの変更であり、内容の変更ではない） |
| そのノードを**遷移先とする**遷移を、未確定の遷移元から作成すること | **可**（遷移の所有者は遷移元のため） |
| 画面の削除 | **可**（確認ダイアログに「確定済みの画面です」と明記する。`RequirementCard`の削除と同じ扱い） |

遷移の編集可否は、**遷移元ノード**のロック状態で決める（遷移先ではない）。

- 確定を解除する機能は、他の画面（KPI・非機能要件）と同様に設けない。
- 確定済みノードを削除すると、そこへ入ってくる遷移（未確定ノードや確定済みノードからのもの）もカスケードで消える。これは許容し、削除確認ダイアログに「接続する遷移もすべて削除されます」と表示する（フェーズ1の文言をそのまま使う）。
- ロックは**UIで隠すだけでなく、必ずServer Action側でも拒否する**（規約33。確定済みの画面を編集できる経路を残さない）。

### 3. 「自動で整列」は元に戻す機能ではなく確認ダイアログにする
ハンドオフは「実行前に確認 or 元に戻す」のどちらでもよいとしている。既存のトースト部品は操作ボタンを持てないため、Undoのために部品を拡張するより、アプリ全体で使っている`confirm()`で「手動で配置した位置がすべて上書きされます。よろしいですか？」と確認する方式を採る。

### 4. ステージの論理サイズを内容に合わせて広げる
ハンドオフのステージは論理サイズ1080×660の固定だが、自動整列は層ごとに270pxずつ右へ進むため、画面が5層以上あると固定ステージからはみ出し、クランプで潰れてしまう。**ステージの論理サイズは`max(既定値, 全ノードの外接矩形＋余白)`として描画ごとに算出する**。ドラッグ中のクランプは、ドラッグ開始時点のステージサイズを使う（ドラッグでステージが際限なく広がらないようにする）。フェーズ1で固定サイズを前提にしている箇所（クランプ・ステージの描画寸法）をgrepで洗い出して修正すること。

## 前提確認

- フェーズ1（Staging反映済み）が完了していること
- ハンドオフの`画面遷移図 7a 高精度デザイン.dc.html`で、`startConnect()`（接続ドラッグ）、`autoLayout()`、ズームツールバー、「この画面を確定」周りの挙動を実際に操作して確認してから着手すること。**`autoLayout()`の座標の原点・余白・層内の並び順は、READMEの要約ではなくHTMLの実装を一次情報として移植する**
- 既存のServer Action（`moveScreenNode`・`addScreenTransition`等）の実際のシグネチャと戻り値を確認してから使うこと（規約50）

## Step 1: ズームを実装する（ほかの操作の前提になるため最初に行う）

- 状態`scale`（0.5〜1.6、0.1刻み、既定1.0）。保存はしない
- キャンバス右下に固定のツールバー`− / 倍率 / ＋ / 100%`を置く。**スクロールコンテナの外側（スクロールしても動かない位置）に重ねる**こと
- ステージは`transform: scale(scale)`（`transform-origin: top left`）で拡縮し、その**外側のラッパーの寸法は論理サイズ×scale**にして、拡大時にスクロールできるようにする
- **フェーズ1のドラッグ処理をscale対応に直す**。これを怠ると、100%以外でノードがカーソルに追従しなくなる。
  - ポインタ座標からステージ内の論理座標への変換は、`ステージ要素.getBoundingClientRect()`を基準に`(clientX − rect.left) / scale`で行う（rectはスクロールとtransformを既に反映しているため、スクロール量の加減算は不要）
  - ノードのドラッグ、クランプ、次Stepのポート接続、ドロップ位置の判定のすべてで同じ変換関数を共用する（重複実装しない）

## Step 2: ポートからの遷移作成を実装する

- ノード右端中央のポートで`pointerdown`すると接続ドラッグを開始する（**ノード自体のドラッグ・選択は開始させない**）。カーソルは`crosshair`、hoverで塗りつぶし
- ドラッグ中、送信元ポートからカーソルまで`#2f5d45`系（既存トークンにマップ）の破線を描画する
- ポインタを離した位置が別ノードの矩形内であれば遷移を作成する。**判定は論理座標での矩形ヒットテスト**で行う（DOMの要素判定に頼らない）。ノードの外で離した場合は何も作らずキャンセル
- 作らない場合：自己ループ、同方向の重複（`(from,to)`が既にある）。重複のときは作成せず、トーストで「既にこの遷移があります」と知らせる
- 遷移元が確定済みのノードの場合は、ポートを表示しない（または無効表示にする）。Server Action側でも拒否する
- 作成後はその遷移を選択状態にし、**右パネルの操作名入力にフォーカス**する（KPI画面の新規作成時フォーカスと同じ仕組みを再利用してよい）
- **作成した遷移のidが再取得データに現れるまでの間、選択を解除しないこと**（`addScreenTransition`が新しいidを返すようにし、パネルは「選択idに対応する遷移が見つかったら表示する」形にする）。再取得が届く前に選択が消えて、フォーカスも失われる状態を作らない
- ポインタイベントは`window`にリスナーを張る場合、確実に解除すること（アンマウント時・pointerup時）。ドラッグ中の呼び出しは`onClick`と同様に例外が`error.tsx`に届かないため、`try/catch`でトースト表示する（規約44）

## Step 3: 「自動で整列」を実装する

**配置ロジックは純粋関数として`src/lib/screen-flow/`に実装する**（DB非依存。`derive.ts`に足すか、`layout.ts`を新設）。

- 入次数0のノードを起点（第0層）にBFSで層分けする。**各ノードの層は最初に到達した時点の層**とする（循環があっても無限ループにならない）
- 層ごとに列（既定270px間隔）、層内で行（既定120px間隔）に配置する。**層内の並び順は`screen_code`昇順など決定的な順序**にし、実行のたびに結果が変わらないようにする
- 起点から到達できないノード（循環だけで構成された部分など）は、第0層の下に並べる
- **入次数0のノードが1つも無い（全体が循環している）場合**は、`screen_code`が最小のノードを起点として扱う
- 座標の原点・余白はハンドオフHTMLの`autoLayout()`に合わせる
- ヘッダーに「自動で整列」ボタンを置く。押すと`confirm()`で確認し、同意した場合のみ実行する
- 位置の保存はまとめて行う`moveScreenNodes(projectId, [{id, x, y}])`を新設する。
  - **更新件数を確認すること**（`.select()`で返った件数が対象件数と一致しなければエラーにする。RLSで弾かれても黙って0件更新になるため。規約47）
  - クライアントは、同じ純粋関数で計算した座標を**上書き値（optimistic overrides）として即座に反映**し、保存の完了後も**実データが追いつくまで上書きを消さない**（規約59。フェーズ1のドラッグ移動と同じ仕組みを、複数ノードに対応させる）
  - 保存に失敗した場合は上書きを取り除いて元の位置に戻し、エラートーストを表示する
- 整列後、全ノードがステージ内に収まること（Step 1の「ステージの論理サイズを内容に合わせて広げる」と合わせて確認する）

## Step 4: 確定ワークフローを実装する

### Server Action
- `confirmScreenNode(nodeId, projectId)`：`status`を`confirmed`に更新する。更新件数を確認する（規約47）
- 改名（`renameScreenNode`）と9章紐付けの変更（`linkScreenFunction`）に、次のロック判定と自動引き上げを追加する。
  - 対象ノードが`isItemLocked`なら`UserFacingError`で拒否する
  - `ai_draft`のノードを改名・紐付け変更した場合は`se_reviewing`に引き上げる（KPI画面フェーズ2と同じ）
- `addScreenTransition`・`updateScreenTransitionLabel`・`removeScreenTransition`に、**遷移元ノード**が`isItemLocked`なら拒否するガードを追加する
- 画面削除（`removeScreenNode`）と位置の保存（`moveScreenNode`／`moveScreenNodes`）にはロックのガードを付けない

### 右パネル（画面ノード選択時）
- ステータスピルを「下書き／要レビュー／確定済」で表示する（フェーズ1で既に表示している場合は、語彙が一致しているか確認する）
- アクションバー（sticky bottom）：未確定なら primary の「この画面を確定」、確定済みなら「✓ 確定済」の静的表示。右端の「画面を削除」は常に表示する
- 確定済みのノードでは、画面名・9章紐付けの変更/解除・遷移先の追加（チップ）・遷移先行の`×`を**非表示または無効**にし、「確定済みのため編集できません」と小さく添える

### 右パネル（遷移選択時）
- 遷移元ノードが確定済みの場合、操作名の編集・「戻りの遷移を追加」・「遷移を削除」を非表示または無効にする

### ヘッダー
- サマリピルに「確定 k/N」を表示する（フェーズ1で未実装の場合は追加する）。要確認の件数は従来どおり、確定の有無に関わらず警告の有無で数える

**注意**：入力欄の`key`は、idだけでなく表示する値も含めること（規約58）。確定やロックの切り替わり、他経路での改名で値が変わっても古い表示が残らないようにする。

## Step 5: 動作確認

実際のブラウザ・DBで確認する。ズームは100%以外（特に50%と160%）で行うこと。

**ズーム**
1. 50%・100%・160%で、ノードのドラッグ中にノードがカーソルへ1:1で追従することを確認する。保存された座標が、見た目の位置と一致することをリロード後に確認する
2. ズームツールバーがスクロールしても右下に固定されていること、拡大時にキャンバスがスクロールできることを確認する

**遷移の作成**
3. ポートから別ノードへドラッグして遷移が作られ、その遷移が選択されて操作名入力にフォーカスが当たることを確認する（ズーム50%・160%でも）
4. 自己ループ・同方向の重複は作られず、重複のときはトーストが出ることを確認する。ノード外で離すと何も作られないことを確認する
5. 作成直後に選択が消えたりフォーカスが外れたりしないことを確認する

**自動で整列**
6. 次のグラフで期待どおりの配置になることを確認する：A→B、A→C、B→D、C→D、孤立ノードE、循環のみのX↔Y（起点から到達できない）。Eは第0層、X・Yは第0層の下に置かれる
7. 全ノードが循環している場合（起点が無い）でも、`screen_code`最小のノードを起点として配置されることを確認する
8. 実行前に確認ダイアログが出て、キャンセルすると何も変わらないことを確認する。実行後にリロードしても配置が保持され、実行直後に元の位置へ一瞬戻るちらつきが無いことを確認する
9. 6画面以上・5層以上のデータで、整列後も全ノードがステージ内に表示され、はみ出して潰れないことを確認する
10. 確定済みのノードを含む状態で整列でき、確定済みノードの位置も動くことを確認する

**確定ワークフロー**
11. 「この画面を確定」で確定済みになり、状態ドット・ピル・ヘッダーの「確定 k/N」が更新されることを確認する
12. 確定済みノードで、画面名・9章紐付け・遷移先の追加/削除・操作名の編集・ポートからのドラッグ・戻りの遷移の追加が**UI上できない**ことを確認する
13. 同じ操作を、UIを経由せず（Server Actionを直接呼ぶ等）実行しても**サーバー側で拒否される**ことを確認する
14. 未確定ノードから確定済みノードへの遷移は作成でき、確定済みノードを遷移先にできることを確認する
15. 確定済みノードを位置移動でき、削除でき（確認ダイアログに「確定済みの画面です」が出る）、削除すると接続する遷移も消えることを確認する
16. `ai_draft`のノードを改名すると`se_reviewing`に変わることを確認する

**回帰**
17. フェーズ1の機能（ノードのドラッグ移動、往復遷移の描画、右パネル3モード、9章への紐付け、遷移の追加・編集・削除、画面の追加・削除、警告表示）に回帰が無いことを確認する

## やってはいけないこと

- ズーム対応を後回しにして、100%でしか確認しないこと（座標変換の誤りは100%では見つからない）
- ロックをUIで隠すだけで済ませること（Server Action側のガードが必須）
- 「自動で整列」の座標計算を、クライアントとサーバーで別々に実装すること（純粋関数を1つだけ持つ）
- 自動整列の保存で、更新件数の確認を省略すること
- 元に戻す（Undo）機能のために、トースト部品を拡張すること（確認ダイアログで済ませる）
- AI素案の差分提案、キーボード操作、Ctrl/⌘+ホイールズーム、パンを本フェーズで実装しないこと
