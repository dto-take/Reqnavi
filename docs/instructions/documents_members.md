# 指示書：資料の削除・案件メンバーの削除・資料登録の失敗時の扱い

## 目的

リリース前に必要と判断した、運用上の欠落を塞ぐ。

| 部 | 内容 |
|---|---|
| A | 資料の登録が失敗したときの扱い：AI分類が失敗しても**未分類として登録**し、あとで再分類できる。登録が失敗したときは、**アップロード済みのStorageのファイルを必ず消す** |
| B | **資料の削除**（誤ってアップロードした顧客資料を、画面から消せるようにする） |
| C | **案件メンバーの削除**（異動・退職などでメンバーを外せるようにする）と、役割の変更（案件ごとの役割がある場合のみ） |

**部ごとに、別のコミット・別の報告**とする（A→B→Cの順）。変更申請の承認・クローズは、本指示書の対象外（リリース後に検討する）。

## 共通の方針（これまでの規約）

- 新しいServer Actionは、`safeAction`で包み、`ActionResult`を返す（規約67）。呼び出し側は`runAction`を使う
- **権限は、UIの出し分けだけでなく、Server Action側で明示的に確認する**（規約33）。判定は`permissions.ts`に集約する
- **サーバーで確かめられる値を、引数で受け取らない。** idだけを受け取り、案件・権限・状態はDBから読み直す（規約66）
- 更新・削除は、`.select()`で**件数を確認**し、0件なら「対象が見つかりません」を返す（規約47）
- Storageの削除は、**ファイルの削除と残存0件の確認が済んでから、DB行を削除する**。失敗したらDB行を残す（規約65）。「ファイルが既に無い」は成功として扱う（再試行できるように）
- 検証は**本番ビルド**（`next build`＋`next start`）で行う。失敗は、案件のメンバーではない`member`のセッションに差し替えて起こす
- 開始前に`git status`で作業ツリーがきれいなことを確認する（規約69）
- マイグレーションを作る場合は、`docs/02_architecture.md`にも反映する

## 前提確認（実装前に、実際のコードとスキーマで調べて報告する）

1. `source_documents`の列、`item_sources`（項目の出典）の**外部キーの削除時の挙動**と、出典に何が保存されているか（資料idだけか、ファイル名や抜粋も含むか）
2. `source_documents`・Storage（`storage.objects`）の**DELETEのRLSポリシー**が、誰に許しているか
3. `project_members`の列。**案件ごとの役割の列があるか**（全体の役割は`user_profiles.user_role`で、`/admin/users`から変更できる）
4. 資料一覧ページ（資料の登録・再分類の画面）と、案件のメンバー管理ページの現状

## 部A：資料の登録が失敗したときの扱い

### A-1 AI分類が失敗しても、未分類として登録する
- 現状、AI分類（利用枠の超過、キーの無効など）が失敗すると、登録自体が失敗して、利用者が資料を入れ直す必要がある
- `registerUploadedDocument`を、**分類のステップだけが失敗した場合は、分類タグを空にして登録する**形に変える。分類に失敗したことが分かるよう、`source_documents`に`classification_failed`（boolean、既定false、NOT NULL）を追加する（マイグレーション）。既存の行は`false`
- 資料一覧：タグが空、または分類に失敗した資料に「未分類」のバッジを出し、既存の「再分類」の操作を使えるようにする。再分類に成功したら、`classification_failed`を`false`に戻す
- アップロード完了のトースト：「N件アップロード完了。M件は分類に失敗したため、未分類で登録しました（資料一覧から再分類できます）」のように、成功と区別して表示する
- **未分類の資料は、AI素案の生成に使われない**（分類タグで資料を選ぶため）。黙って除外されないよう、資料一覧のページと、一括生成ページに、「分類されていない資料がN件あります。再分類するまで、AI素案の生成には使われません。」という案内を表示する（N＝タグが空、または分類失敗の資料の数）
- 分類以外の失敗（DBの登録エラー、重複、権限）は、これまでどおり**登録しない**（A-2へ）

### A-2 登録に失敗したら、アップロード済みのファイルを消す
ファイルはクライアントからStorageへ直接アップロードされるため、その後の登録が失敗すると、ファイルだけが残る（画面から見えず、消せない）。
- サーバー側（`registerUploadedDocument`の失敗経路）で、**そのファイルをStorageから削除する**。削除は、利用者自身のクライアント（RLSが効く）で行うことを第一とし、そのためのDELETEポリシーが無ければ、**案件メンバー**に限って許すポリシーを追加する
- **削除してよい条件を、サーバー側で確かめる**（クライアントが渡す`storagePath`を信用しない）：パスが`{projectId}/uploads/`で始まること、**そのパスを参照する`source_documents`の行が存在しないこと**。条件を満たさないときは削除しない（他の資料のファイルを消す経路を作らない。規約66）
- クライアント側でも、Server Actionの呼び出し自体が通信で失敗した場合に、`storage.remove`を**ベストエフォートで試みる**（失敗しても利用者への通知は元のエラーのまま）
- 存在しない案件・権限のない案件の`storagePath`を渡されても、何も削除されないこと

### 検証（部A）
- 有効でないAIキーで起動し、資料をアップロード → 未分類で登録され、バッジ・案内・トーストが出る。有効なキーに戻して再分類 → タグが付き、`classification_failed`が`false`になる
- 未分類の資料があるとき、一括生成ページに案内が出る
- 登録が失敗する状況（案件のメンバーではない`member`で呼ぶ、等）で、Storageにファイルが残らない（`storage.objects`で確認）
- **別の資料のパスを渡して失敗させても、その資料のファイルは消えない**（直接呼び出しで確認）
- 通信を中断した場合に、クライアントが削除を試みる
- 重複のスキップ、成功の経路は従来どおり

## 部B：資料の削除

### 仕様
- **削除できる人**：案件のメンバーである`admin`・`pm`のみ（`permissions.ts`に判定を追加）。`member`・`partner`には、削除の操作を表示せず、サーバー側でも拒否する。RLSがより広く許している場合は、アクション側の確認で絞り、RLSの変更が必要なら報告する
- **操作**：資料一覧の各行に「削除」（`Menu`の「⋯」の中でよい）。確認ダイアログに、**この資料を出典とする項目の件数**を表示する：「この資料を出典とする項目が N 件あります。削除すると、出典の表示が『削除された資料』になります。項目の内容は残ります。」
- **削除の順序**（規約65）：①権限と、資料の存在を確認 ②Storageのファイルを削除（既に無ければ成功扱い）し、残っていないことを確認 ③DBの`source_documents`の行を削除（件数確認）。②が失敗したらDB行を残してエラーを返す
- **出典の扱い**：前提確認1の結果で決める。既定は、`item_sources`の行を**残し、資料への参照だけを外す**（`ON DELETE SET NULL`相当）。出典を表示する画面（項目のカードの「出典N件」、出典の一覧）は、参照が外れた出典を**「削除された資料」**と表示して、画面が壊れないこと。出典の行が資料idをNOT NULLとして持っている等で、この方式が取れない場合は、実装前に報告して相談する
- 削除した資料は、AI素案の生成の対象から外れ、案件トップの資料件数・「最近の資料」・資料一覧から消える。項目の内容、ベースラインのスナップショットには影響しない

### 検証（部B）
- `pm`・`admin`が削除できる。`member`・`partner`は、操作が出ず、直接呼んでも拒否され、DB・Storageが不変
- 確認ダイアログの件数が正しい。削除後、Storageのファイルと`source_documents`の行がともに0件
- 出典の表示が「削除された資料」になり、項目の内容は残る。出典を持つ項目のカード・一覧が壊れない
- Storageの削除が失敗する状況（サービスキー等を無効にして起動）で、**DB行が残り**、フォーム／トーストに日本語の理由が出る。**再試行で成功する**
- 既にファイルが無い資料を削除できる（冪等）
- 他の案件の資料のidを渡しても削除できない
- 案件トップ・資料一覧・一括生成の対象に、削除が反映される

## 部C：案件メンバーの削除（と、案件ごとの役割の変更）

### 仕様
- **外せる人**：案件のメンバーである`admin`・`pm`（メンバー追加と同じ条件。`permissions.ts`を共用）
- **操作**：メンバー一覧の各行に「外す」と確認ダイアログ：「〇〇さんを、この案件から外します。作成・編集した内容と工数記録は残ります。」
- **ガード**：**案件に、`pm`または`admin`のメンバーが最低1人残る**こと。最後の1人を外す操作は、サーバー側で拒否する（「この案件には、管理者またはPMのメンバーが最低1人必要です」）。自分自身を外す操作は、このガードを満たすかぎり許可する
- 外したメンバーは、その案件にアクセスできなくなる（404になる）。**そのメンバーが作成・編集した項目、工数記録は、削除しない**
- **役割の変更**：前提確認3の結果で決める。
  - **案件ごとの役割の列が無い場合**：役割は全体の役割（`/admin/users`で変更できる）であり、案件ごとの役割は存在しない。**この場合、役割変更は実装せず、その旨を報告する**（案件ごとの役割の新設は、データモデルの変更が大きいため、実装せずに相談する）
  - **案件ごとの役割の列がある場合**：`admin`・`pm`が変更できるようにし、「最低1人のpm／adminが残る」ガードを、役割を下げる操作にも適用する

### 検証（部C）
- `pm`が`member`を外す → そのメンバーは案件を開けない（404）。その人の項目・工数記録は残る
- 最後の`pm`／`admin`を外す操作が拒否される。自分自身を外す（他に`pm`がいる場合は成功、いない場合は拒否）
- `member`・`partner`は、操作が出ず、直接呼んでも拒否され、DBが不変
- 存在しないメンバー、別の案件のメンバーのidを渡しても、何も起きない（件数0で「対象が見つかりません」）
- 外したメンバーを、再度追加できる

---

## やってはいけないこと

- クライアントが渡す`storagePath`・案件id・権限を、そのまま信用して削除すること
- Storageの削除を確認する前に、DB行を削除すること
- 資料を削除したときに、項目の内容や出典の行まで消すこと
- 案件ごとの役割の列が無いのに、新設して実装を進めること（相談する）
- 変更申請の承認・クローズを、本指示書で実装すること
- 部A・B・Cを、1つのコミットにまとめること
