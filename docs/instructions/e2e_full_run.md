# 指示書：通しの動作確認（サンプル資料による全機能のE2E検証）

## 目的

リリース前の最終確認として、サンプル資料を使い、**案件の作成から資料の取り込み、AI素案の生成、編集・確定、確定判定、出力、権限、削除まで**を、実際のブラウザ・DB・Geminiで一通り流す。改修を重ねたため、機能同士のつながりで壊れている箇所が無いかを洗い出すことが目的である。

**この指示書では、不具合を見つけても修正しない。** 再現手順・証跡・原因の見立てを報告し、修正の要否と優先度は報告を見てから決める（検証中に直してしまうと、何を直したかが追えなくなり、再検証の範囲も曖昧になる）。

## 実行方針

- **実行環境はローカル**（ローカルのSupabase＋dev server）とする。Stagingの実データを汚さないため。ローカルで確認できない項目（Googleログイン、Vercelの関数実行時間、Staging上のStorage）は、末尾の「手動確認」に回す
- Geminiは**実際に呼ぶ**。呼び出し回数と所要時間を記録する（目安：合計60回以内）。回数は`ai_interactions`の件数で数える
- コード・マイグレーションは**変更しない**。テスト用のスクリプトは作業用の領域（リポジトリ外または未追跡の一時ディレクトリ）に置き、終了時に削除する
- ブラウザ自動化は`finally`で`browser.close()`を保証し、終了後に孤立プロセスが残っていないことを確認する（規約51）
- **途中経過を、報告書に追記しながら進める**。dev serverがWindowsのリソース不足で止まることがあるため、グループ（A〜）ごとに区切り、必要なら`.next`を消してdev serverを再起動して続行する。続行できない場合は、そこまでの結果を報告して止める
- 検証全体を通して、**ブラウザのコンソールエラー、Reactのハイドレーション警告、未処理のPromise拒否**を記録し、発生した操作を報告に添える

## 前提確認（実行前に、ユーザーに確認すること）

- ローカルSupabaseが起動しており、`.env.local`の`GEMINI_API_KEY`が**課金（クレジット購入済み）の有効なキー**であること。`OWN_COMPANY_EMAIL_DOMAIN`が設定されていること
- **サンプル資料（`sample-docs/`の01〜09）の置き場所のパス**を、ユーザーに確認する
- **実際の顧客資料は使わない**。使いたい場合は、Geminiの契約条件（TD-001）の確認状況を踏まえ、ユーザーの明示的な許可を得ること。サイズ・形式の検証には、内容が架空の合成ファイルを作って使う（例：サンプルのPPTXに画像を加えて数MBにしたもの、複数ページのPDF）
- テスト用のアカウントを用意する：admin、pm、member、partnerの各ロール（ローカルの既存ユーザーに無いものは、`/admin/users`の画面操作で作成する）。**Googleログインはローカルでは検証しない**（手動確認に回す）
- 権限の期待値は、`docs/01_requirements.md`と`docs/02_architecture.md`の記載から読み取る。記載が曖昧な箇所は、判断せず「期待値が不明」として報告する

## 報告書

`docs/e2e/e2e-report-YYYYMMDD.md`（日付は実行日）に、次の構成で作成する。

1. サマリ：実行日時、所要時間、Gemini呼び出し回数と最長の所要時間、○（合格）／△（軽微な問題）／×（不具合）／－（未実施・不能）の件数
2. シナリオ別の結果表：`ID／手順／期待結果／結果／証跡（スクリーンショットのパス、SQLの結果など）／備考`
3. **不具合一覧**：`ID／重大度（Blocker：リリースを止める／Major：リリース前に直す／Minor：後で直してよい）／再現手順／期待と実際／原因の見立て／関連する画面・ファイル`
4. 気づいた点（不具合とは言えないが、改善の余地があるもの）
5. 手動確認が必要な項目の一覧

## シナリオ

各ステップで、画面の見た目、DBの状態（件数・状態）、エラーの有無を確認する。AIが生成した内容は、**各章3件ほどを抜き取り、元の資料と照合**し、資料に無い事実を断定していないかを判定する。

### A. 案件の作成（pm）
- A1 顧客を作成し、案件を新規作成できる。対象章の設定（一部の章を外す）ができ、外した章がサイドバー・案件トップ・案件一覧に現れない
- A2 作成直後の案件が、案件一覧に反映される。案件トップが空の案件として破綻なく表示される（「次にやること」が最初の章を指す）

### B. 資料の取り込み
- B1 サンプル9ファイル（Markdown・PDF・Excel・PowerPoint）を**一括でドラッグ＆ドロップ**でき、すべて取り込める。各資料の分類タグを記録し、内容と照らして妥当かを判定する（特に、KPI設計資料に「KPI」が付くか）
- B2 20MBを超えるファイルが、アップロード前に弾かれる。数MBの合成PDF・PPTXが取り込める
- B3 同じ資料を再アップロードしたときの挙動（重複の扱い）を記録する

### C. AI素案の生成
- C1 AI素案の一括生成（1〜3、5〜9、11〜14章）。章ごとの生成件数を記録する。**0件の章は、分類タグ・資料の内容を確認し、正当な0件（該当する資料が無い）か不具合かを判定**する
- C2 4章（KPI）：AI素案の生成で、ゴール→目標→戦略→戦術の階層ができる。ノード単位のAI候補（採用・見送り・すべて採用・別の案）が動く
- C3 10章（非機能要件）：標準観点を採用し、方針を編集し、チェック項目を追加し、AI候補を採用・見送りできる
- C4 業務フロー：As-Is／To-BeのAI生成（0件のときのみ）。業務フロービルダーで、ノードの追加・条件分岐・編集・業務手順表・ユースケース記述・CSV出力が動く
- C5 画面遷移図：9章の画面情報から、AI素案（差分提案）が出て、採用・見送り・一括操作ができる。ポートからの遷移作成、自動で整列、ズーム、確定が動く
- C6 15章（進捗）：大工程・中工程を作り、依存関係を設定し、ドラッグで期間を変えると後続が追従する
- C7 **再生成**：1つの章で項目を確定してから再生成し、確定した項目が残り、AI素案（未確認）だけが置き換わる

### D. 編集と確定
- D1 各章（A/B/C章）のカード表示：グループ化、フィルタ、チェックボックスによる一括確定・不採用・グループ変更、削除、並べ替え、「未入力」からの入力
- D2 曖昧表現チェック（辞書）とAI判定（詳細）が動き、本文にインライン表示される。リスク許容での確定（理由入力）が動く
- D3 確定済みの項目・KPIノード・観点・画面が、編集できなくなる。UIを経由しない操作（Server Actionを直接呼ぶ等）でも拒否されることを、各画面で1つずつ確認する
- D4 「次にやること」が、編集の進み具合に応じて、曖昧表現のある章・最終編集が新しい章を指す

### E. 確定判定
- E1 確定判定ダッシュボード・サイドバー・案件トップ・案件一覧の**章ごとの数値と状態が、すべて一致**する（4・10・15章を含む）
- E2 確定できる章をすべて確定すると、案件一覧が「完了」になり、確定可能な章のセグメントがすべて緑になる
- E3 整合性チェックが動き、誤検出（4章・10章の行を孤立と判定する等）が無い
- E4 ベースラインを確定でき（v1）、項目を変更すると差分管理に出る。再度ベースラインを確定すると版番号が進み、旧版が`superseded`になる
- E5 変更申請（変更管理）の流れが、これまでどおり動く

### F. 出力
- F1 Word、PowerPoint（サマリー）、PowerPoint（詳細・全章）、画面設計書（Excel）、業務手順表（CSV）を、案件トップ・各画面から出力できる。生成中の表示が出て、日本語のファイル名が崩れない
- F2 出力ファイルを実際に開き（`python-docx`、`python-pptx`、`openpyxl`等で解析してよい）、日本語の文字化け・欠落・件数の食い違い（画面の件数との比較）が無い

### G. 権限（admin／pm／member／partner）
- G1 ロールごとに、案件一覧・案件トップ・章ページ・資料・工数記録・ベースライン・メンバー・案件設定で、見える範囲とできる操作が、権限の設計どおり
- G2 パートナーに非公開の項目・数値が、案件トップの「最近の動き」・章の進み具合・サイドバーに出ていない
- G3 管理者が、自分がメンバーではない案件を開いたとき、案件一覧・案件トップとも「進捗は表示されません」となる
- G4 管理者以外が、管理者専用の操作（ユーザー作成、案件削除）を、UIからも直接の呼び出しからも実行できない

### H. 案件横断連携
- H1 同じ顧客の2つの案件で、双方がオプトインしたときだけ、横断参照ができる。片方だけでは参照できない
- H2 横断参照を有効にしても、案件一覧・案件トップ・ダッシュボードの数値に、他案件の項目が混ざらない（規約62）

### I. エラー系
- I1 保存中にServer Actionの通信を中断すると、日本語のトーストが出て、楽観的に更新していた画面（ドラッグ・並べ替え）が元に戻る
- I2 AI生成中の失敗（キーの無効化はしない。生成中に通信を中断する）で、日本語のエラーが出て、画面が固まらない
- I3 権限の無い操作・存在しない案件IDへのアクセスで、適切なエラー画面になる

### J. 画面幅
- J1 主要な画面（案件一覧・案件トップ・各章・KPI・非機能要件・進捗・画面遷移図・業務フロー・ダッシュボード）を、1440／1100／900pxで開き、崩れ（横スクロール・重なり）が無い。スクリーンショットを残す

### K. 案件の削除（最後に実行）
- K1 管理者が案件を削除（案件名の入力確認つき）すると、関連するすべてのテーブルの行と、Storage上の資料ファイルが残らない（`project_id`を持つ全テーブルと`storage.objects`の件数を、削除前後で比較する）。案件一覧から消える

## 手動確認が必要な項目（報告書に一覧で添える）

ローカルでは検証できないため、ユーザーがStagingで確認する。

- Googleログイン（自社ドメインの初回自動登録、再ログイン、他ドメインの未登録の拒否、他ドメインの事前登録済みの許可）
- Vercel上のAI生成の所要時間（ローカルで測った最長の呼び出し時間を、プランの関数実行時間の上限と比較する材料として報告する）
- Staging上でのファイルアップロード（数MBのPDF・PPTX）
- パートナー権限での案件トップ（Stagingのテストユーザー）

## やってはいけないこと

- 不具合を見つけたときに、コード・マイグレーションを修正すること（報告のみ）
- 実際の顧客資料を、ユーザーの許可なくGeminiへ送ること
- Stagingや本番の環境・データに接続・操作すること
- 検証用のテスト用データ・ユーザー・プロセスを、終了後に残すこと
