# 指示書：第2回の通しの動作確認（修正の再検証と、第1回で未実施だった項目）

## 目的

第1回のE2E（`docs/e2e/e2e-report-20261005.md`）のあと、次の修正を入れた。**リリース前の最終確認として、これらを一通り再検証し、第1回で未実施だった項目を実施する。**

- 第1弾：確定済み項目の保護、他案件の参照の条件、案件削除時のStorage
- 第2弾：権限別のUI・404・パートナーの非公開章・重複アップロード・通信断・入力欄の復元・KPI候補・ヘルプボタン・出力の整合・日本語PDFの分類・再生成の重複
- 資料・メンバー：未分類での登録、資料の削除、メンバーの削除
- Server Actionのエラー処理の移行（本番ビルドで日本語の理由が届く形）
- 本番ビルドでのOffice形式のテキスト抽出の修正
- AI素案の置き換えの順序（失敗しても既存の素案が残る）

**第1回と同じ方針とする**（`instructions_e2e_full_run.md`の「実行方針」「前提確認」「報告書」「やってはいけないこと」を踏襲する）。要点：

- 実行環境は**ローカルの本番ビルド**（`next build`＋`next start`）。ローカルのSupabase、実際のGemini（課金のキー）
- **不具合を見つけても修正しない。** 再現手順・証跡・原因の見立て・重大度（Blocker／Major／Minor）を報告する
- コード・マイグレーションを変更しない。テスト用のスクリプトは作業用の領域に置き、終了時に削除する
- ブラウザ自動化は`finally`で`browser.close()`を保証し、孤立プロセスを残さない（規約51）
- 実際の顧客資料は使わない。サンプル資料（`sample-docs/`の01〜09）と、内容が架空の合成ファイルを使う
- 報告書：`docs/e2e/e2e-report-YYYYMMDD-round2.md`

## 実行前の準備（重要）

- **並行して動く検証・開発サーバーが無いこと**を確認する（第1回の後の検証で、並行した検証が原因とみられる誤判定があった）。ローカルのDBは、**新しい状態（`supabase db reset`）から始める**
- 作ったばかりのセッションでは、「JWT issued at future」の一時エラーが出ることがあるため、ユーザー作成後に30秒ほど待ってから使う
- 失敗ケースは、**案件のメンバーではない`member`のセッションに差し替えて**起こす。差し替えは、Server Actionを送った直後に`pm`へ戻す（失敗後の再取得で画面が404になり、元に戻ったかを確認できなくなるため）
- ユーザーは、`admin`・`pm`・`member`・`partner`の4ロールを用意する
- 検証の前後で、`npm run check:actions`（違反0件）、型チェック（エラー0件）、ESLint（エラー0件）、`next build`の成功を確認し、報告書に記録する

## 報告の形式

第1回と同じ（サマリ／シナリオ別の結果表／不具合一覧／気づいた点／手動確認の一覧）。サマリに、**Gemini呼び出し回数と、呼び出しごとの所要時間（特に章の一括生成）**を記録する（Vercelの関数実行時間の上限と比べる材料にする）。

### N. 追加した機能の検証

| 項目 | 確認する内容 |
|---|---|
| N1 | **未分類での登録**：AIのキーを無効にしてアップロードすると、未分類で登録され、バッジ・案内（資料一覧と一括生成ページ）・トーストが出る。有効なキーで再分類すると、タグが付き、`classification_failed`が戻る |
| N2 | **登録失敗時のファイル削除**：登録が失敗する状況で、Storageにファイルが残らない。**他の資料のパスを渡して失敗させても、その資料のファイルは消えない** |
| N3 | **資料の削除**：pm・adminだけが削除できる。確認ダイアログに、出典の件数が出る。削除後、Storageのファイル・資料の行・出典が消え、項目の内容は残る。member・partnerは、操作が出ず、直接呼んでも拒否される。Storageの削除が失敗する状況で、DB行が残る |
| N4 | **メンバーの削除**：pm・adminが外せる。**最後のpm／adminは外せない**。外したメンバーは案件が404になり、そのメンバーの項目・工数記録は残る。再追加できる。member・partnerは拒否される |
| N5 | **Office形式のテキスト抽出（本番ビルド）**：xlsx・pptx・docx・PDF（テキストあり）で、分類のログの`text_length`が0でなく、タグが中身に基づく。11章（xlsx由来）と3章（pptx由来）のAI素案が、資料の内容に基づく項目を作る。抽出が空になる資料（本文なしのdocx等）では、「テキストを取得できませんでした」が出る |
| N6 | **Server Actionの日本語の理由（本番ビルド）**：ロック中の拒否、権限、重複、入力不正が、トースト・インラインに日本語で出る。英語の長文・汎用のエラー画面が出ない。主な画面（要件項目・KPI・非機能要件・進捗・画面遷移図・業務フロー・案件設定・メンバー・ベースライン・変更申請・資料）で、各1つ以上確認する |

| N8 | **確定率の定義の一貫性**：ダッシュボード・サイドバー・案件トップ・案件一覧・PowerPointの確定率・章ごとの状態が、4・10・15章を含めて一致する |
| N9 | **監査ログ**：資料の削除・メンバーの削除・案件の削除・ベースラインの確定の各操作で、記録がちょうど1行でき、内容が正しい。失敗した操作では記録されない。案件を削除しても、その案件の記録が残り、案件名・顧客名が表示される。`admin`だけが`/admin/audit-logs`を開ける。`authenticated`のJWTでの`insert`・`update`・`delete`が拒否される。資料の内容・項目の本文が記録に含まれない |
