# 指示書：要件定義画面UX改善 フェーズ5（視覚的な仕上げ）

## 目的

1. 曖昧表現を、本文中の該当箇所に下線・背景色でインライン表示する
2. ドラッグが困難な利用者のため、キーボードでも並び替えができる代替手段を用意する
3. 章フッターの表示を、カード型レイアウトに合わせて整える

## スコープの調整

- **新しい書体（Shippori Mincho・IBM Plex Mono）の追加は行わない**。フェーズ1で確立した方針（Inter一本化を崩さない）を本フェーズでも維持する
- **完全なキーボードドラッグ操作は実装しない**。ハンドオフ自身が代替案として挙げている「⋯メニューの『上へ／下へ移動』」の方が実装コストに見合うため、そちらを採用する

## 重要な前提：曖昧表現のインライン表示には、これまで保持していなかった情報が必要

現在の`ambiguous_flags`（jsonb）は`{source, reason?}`のみを保持しており、**本文中のどの文字列が該当箇所かという情報（実際のフレーズ文字列）を持っていない**。インライン表示を実現するには、まずこの情報を追加で保持する必要がある。

## 前提確認

- 要件定義画面UX改善 フェーズ1〜4が完了していること
- ハンドオフの「項目カード（展開形）」節の「曖昧表現のインラインマーク」に関する記述、「11. 曖昧表現」節を再確認してから着手すること

---

## Step 1: 曖昧表現フラグに該当フレーズを追加

`ambiguous_flags`はjsonb列のため、スキーマ変更は不要。以下の既存ロジックを修正し、検出時に該当フレーズの文字列を含めるようにする。

1. `src/actions/ambiguous-check.ts`の辞書ベース検出：マッチした文字列そのものを`phrase`として`ambiguous_flags`に含める
2. AI判定（`ambiguous_check_l2`プロンプト）：該当箇所の文字列（`phrase`）も返すようプロンプトを修正する（新バージョンとして登録、既存のプロンプトバージョン管理方針を踏襲する）

```ts
type AmbiguousFlag = {
  source: "dictionary" | "ai" | "extraction";
  reason?: string;
  phrase?: string;
};
```

**注意**：`extraction`由来（AI素案生成時に付与されるもの）は元々フレーズ情報を持っていない可能性が高い。`phrase`が無い場合はインライン表示せず、従来通りバッジのみの表示にフォールバックすること。

## Step 2: インライン表示用のレンダリング関数を作成

新規ファイル `src/lib/highlight-ambiguous.ts`（通常モジュール、DBに依存しない純粋関数）。

```ts
export function highlightAmbiguousPhrases(
  text: string,
  flags: { phrase?: string; reason?: string }[]
): { segments: { text: string; isAmbiguous: boolean; reason?: string }[] } {
  // phraseを持つflagについて、textの中から最初に一致する箇所を検索し、
  // ambiguousな箇所とそうでない箇所に分割したセグメント配列を返す。
  // 同じフレーズが複数回出現する場合は最初の1箇所のみをハイライトする簡易実装でよい。
}
```

`src/components/domain/requirement-table/RequirementCard.tsx`の本文表示部分で、この関数を使ってセグメントごとにレンダリングする。

```tsx
{segments.map((seg, i) =>
  seg.isAmbiguous ? (
    <mark
      key={i}
      className="bg-[#FBEAE5] border-b-2 border-[#CF7F66] cursor-pointer"
      title={seg.reason}
      onClick={() => setActiveAmbiguousReason(seg.reason)}
    >
      {seg.text}
    </mark>
  ) : (
    <span key={i}>{seg.text}</span>
  )
)}
```

クリック時の挙動は、実装のシンプルさを優先し、まずは`title`属性によるツールチップ表示＋クリックで既存の「⋯」メニューを開く、という最小限の実装でよい。

## Step 3: キーボード操作の代替（⋯メニューへの追加）

`RequirementCard.tsx`の「⋯」メニューに、「上へ移動」「下へ移動」を追加する。

```tsx
<button onClick={() => handleMoveUp(item.id)}>上へ移動</button>
<button onClick={() => handleMoveDown(item.id)}>下へ移動</button>
```

**注意**：グループ軸が「要件区分」以外（フェーズ4で並び替え自体を無効化した状態）のときは、この「上へ移動」「下へ移動」もメニューから非表示にする。移動のロジックは、フェーズ2の`moveItemToGroup`を流用できる。

## Step 4: 章フッターの仕上げ

既存の章フッター（前の章／次の章ナビゲーション）を、カード型レイアウトに合わせて余白・区切り線を調整する。ハンドオフの「章フッター」節を参考に、視覚的な一貫性を持たせる（具体的な数値調整はお任せする）。

## Step 5: 動作確認

1. 辞書ベースの曖昧表現検出を実行し、本文中の該当フレーズに下線・背景色が付くことを確認する
2. AI判定（詳細）を実行し、同様にインライン表示されることを確認する（`phrase`が返らないケースがあれば、バッジのみの表示にフォールバックすることを確認する）
3. インライン表示された箇所をクリックし、理由が確認できることを確認する
4. 「⋯」メニューの「上へ移動」「下へ移動」で、カードの順序が正しく入れ替わることを確認する
5. グループ軸を「ステータス」に切り替えた状態では、「上へ移動」「下へ移動」がメニューに表示されないことを確認する
6. 章フッターの表示が、カード型レイアウト全体と視覚的に馴染んでいることを確認する
