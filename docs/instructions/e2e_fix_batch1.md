# 指示書：E2E指摘の修正 第1弾（権限・データ保護。リリース前に必ず直す3件）

## 目的

E2E検証（`docs/e2e/e2e-report-20261005.md`）で見つかったMajor 3件を修正する。いずれも「UIでは防げているが、サーバー側の条件が足りない」という同じ型の問題である。

| ID | 内容 |
|---|---|
| B-D3-item | 確定済みの要件項目（A/B/C章）が、UIを経由しないServer Action呼び出しで書き換えられる |
| B-H1 | 他案件の参照一覧が、オプトインの有無・確定状態に関わらず、自分がメンバーの別案件の全項目を表示する |
| B-K1 | メンバーではない管理者が案件を削除すると、DB行は消えるが、Storage上の資料ファイルが残る |

## 共通の方針

- **UIで隠す・無効にするだけで済ませない。サーバー側で必ず拒否する**（規約33）
- 更新・削除の結果は、**更新件数を確認する**（RLSで拒否されても`error: null`・0件になる。規約47）
- エラーは`UserFacingError`＋`errorMessage()`で返す（規約43）
- 検証は、**UIを経由しない呼び出しで行う**（E2Eで使った方法：画面操作で発生したServer ActionのPOSTを捕捉し、対象のidを差し替えて再送する）
- 修正後、E2E報告書の該当項目（D3-item、H1b、K1、K1b）を再実行し、結果を報告書に追記する
- 本指示書の範囲外の不具合を見つけた場合は、直さず報告する

## 修正1：確定済みの要件項目を、サーバー側で守る（B-D3-item）

### 原因
`updateRequirementItemContent`、`markAsRejected`、`markAsExceptionApproved`、`updateRequirementItemStatus`などが、更新前に対象行のstatusを確認せず、`.update().eq("id")`だけを行っている。KPIノード・非機能要件の観点・画面遷移図は、同じ操作で拒否できている。

### 手順
1. `src/actions/requirement-items.ts`の**すべてのexportされたServer Actionを一覧にし**、次のとおり分類して報告する（grepで洗い出し、記憶に頼らない）。

| 分類 | 扱い |
|---|---|
| 内容の変更（`content`の書き換え、区分（`category`）の変更を含む） | **未確定（`ai_draft`・`se_reviewing`）の項目のみ許可**。確定・例外承認・不採用の項目は拒否 |
| 状態の遷移（確定・例外承認・不採用・確認中への変更） | **未確定の項目からのみ許可**。確定・例外承認・不採用の項目からの遷移は拒否（確定の解除は設けない） |
| 削除 | **ロックを問わず許可**（既存の仕様。確認ダイアログつき） |
| 同じグループ内での並べ替え（`order_index`のみ） | **ロックを問わず許可**（配置であり、内容ではない） |
| 曖昧表現フラグの書き込み（チェックの結果） | **ロックを問わず許可**（分析のメタデータであり、内容ではない） |

2. **区分（`category`）の変更は、内容の変更として扱う。** 別のグループへの移動（`moveItemToGroup`の異なるグループへの移動、`bulkSetCategory`）は、確定済み・例外承認・不採用の項目を**拒否**する（一括操作では、ロックされた項目だけを除外して他は実行し、除外件数を返す。`bulkConfirm`のロックガードと同じ作り）。同じグループ内の並べ替えは許可のまま
3. ガードは、**対象行のstatusを取得して`isItemLocked`で判定するだけでなく、更新の`WHERE`条件にもstatusを含める**（例：`.in('status', ['ai_draft','se_reviewing'])`）。確認と更新の間に別の操作で確定された場合も守れるようにするため。更新件数が0なら、ロックされている（または存在しない）とみなして`UserFacingError`で拒否する
4. UI側（`RequirementCard`等）の無効化は、今のまま残す。サーバーのガードが主、UIは補助

### 検証
- 分類表の**各アクション×各状態（`ai_draft`・`se_reviewing`・`confirmed`・`exception_approved`・`rejected`）**で、許可・拒否が上の表どおりであることを、直接呼び出しで確認し、表にして報告する
- 確定済みの項目で、内容・区分・状態を変えようとするすべての経路が拒否される。拒否されたあと、DBの値が変わっていない
- 未確定の項目の編集・確定・不採用・例外承認・削除・並べ替え・グループ移動が、これまでどおり動く（回帰）
- 確定済みの項目を含む一括操作で、未確定の項目だけが処理される

## 修正2：他案件の参照に、条件を明示的に課す（B-H1）

### 原因
`listCrossProjectReferences`は`.neq(project_id)`で取得するだけで、可視性をRLSの`can_view_cross_project_item`に任せている。しかし**利用者がもう一方の案件のメンバーでもある場合、メンバー用のポリシーで他案件の全行が読めてしまう**。RLSの許可ポリシーは論理和で効くため、横断参照用ポリシーが課している条件（オプトイン、確定済みのみ）は効かない（規約64）。

これは情報の漏えいではない（利用者は元々その案件を読める）が、「双方がオプトインしたときだけ、確定済みの項目だけを参照できる」という機能の約束を守れていない。取り込み（`copyReferenceItem`）も同じ。

### 手順
1. `listCrossProjectReferences`と`copyReferenceItem`で、**アクション側の条件として**次を明示的に課す。**利用者がメンバーであるかどうかに関わらず、同じ条件を適用する**。
   - 自案件と参照元の案件が**同じ顧客**であること
   - **双方の案件がオプトイン済み**であること（どちらか一方でも未オプトインなら、参照・取り込みとも拒否）
   - 参照・取り込みの対象は、**確定済み（`confirmed`・`exception_approved`）の項目のみ**。不採用・未確定は含めない
2. 条件を満たさない場合、参照ページには「他案件の参照は、双方の案件で有効にしたときに利用できます」のような案内を表示する（オプトインの設定画面への導線があれば添える）
3. RLSの`requirement_items_cross_project_select`（非メンバー向け）は、**変更しない**
4. 横断参照の仕様（同じ顧客・双方オプトイン・確定済みのみ）を、`docs/02_architecture.md`に明記する

### 検証
次の組み合わせで、参照一覧の件数と取り込みの可否が期待どおりであること（表にして報告する）。

| 利用者 | 自案件のオプトイン | 参照元のオプトイン | 期待 |
|---|---|---|---|
| 両方の案件のメンバー | OFF | OFF | 参照・取り込みとも不可 |
| 両方の案件のメンバー | ON | OFF | 不可 |
| 両方の案件のメンバー | ON | ON | **確定済みの項目のみ**表示・取り込み可 |
| 自案件のメンバーのみ | ON | ON | 確定済みの項目のみ表示・取り込み可（従来どおり） |
| 自案件のメンバーのみ | ON | OFF | 不可 |
| 別の顧客の案件 | ON | ON | 不可 |

- UIを経由せず`copyReferenceItem`を呼んで、未確定の項目・未オプトインの案件の項目を取り込めないこと
- 集計（案件一覧・案件トップ・ダッシュボードの数値）に、他案件の項目が混ざらないこと（規約62。回帰）

## 修正3：案件削除で、Storage上のファイルも確実に消す（B-K1）

### 原因
`deleteProject`が、削除前に`supabase.storage.list()`でファイルを列挙してから`remove`する作りになっている。StorageのSELECTポリシー（`project_documents_select`）は案件メンバーのみを許すため、**メンバーではない管理者の一覧は空になり（エラーにならない）、`remove`が呼ばれない**。DB行だけが消え、顧客資料のファイルがStorageに残る。

### 手順
1. `deleteProject`を次の順序に直す。
   1. 管理者であることを確認する（既存の`assertAdmin`）
   2. **service-roleのクライアント（既存の`createAdminClient`。サーバー側のみで使う）で**、`project-documents`バケットの`{projectId}/`配下を、**ページングしながら最後まで再帰的に列挙**する（件数の上限に注意。100件ずつ・サブフォルダを含む。取りこぼさない）
   3. 列挙したすべてのファイルを削除する
   4. **削除後に、同じ範囲を再度列挙し、残りが0件であることを確認する**
   5. 0件を確認できたら、DB行を削除する（既存の処理）
2. **Storageの削除や残存確認に失敗した場合は、DB行を削除せず、エラーを返す**（再試行できる状態を保つ。DBだけ消えてファイルが残る状態を作らない。規約65）
3. service-roleのクライアントは、サーバー側のコードでのみ使い、ブラウザに送られるコードからimportしない

### 検証
- **メンバーではない管理者**が案件を削除したとき、DB行とStorageのファイルが**ともに0件**になる
- メンバーである管理者・PMが削除した場合も同様
- **100件を超えるファイルを持つ案件**（合成の小さなファイルでよい）で、全件が削除される
- Storageの削除が失敗する状況を人為的に作り（例：存在しないバケット名にする等）、**DB行が削除されず、エラーが返る**
- 管理者以外が削除を実行できない（回帰）
- 孤立ファイルの有無を調べる読み取り専用のSQL（下記）を、ローカルで実行し、結果を報告する

```sql
-- 存在しない案件のフォルダ配下に残っているファイル（孤立ファイル）の件数
select split_part(o.name, '/', 1) as project_id, count(*) as files
from storage.objects o
left join projects p on p.id::text = split_part(o.name, '/', 1)
where o.bucket_id = 'project-documents' and p.id is null
group by 1;
```

## やってはいけないこと

- UIの無効化だけで済ませること（サーバー側のガードが主）
- 確定済みの項目の削除・並べ替え・曖昧表現フラグの書き込みまで拒否すること（上の表のとおり許可を維持する）
- 横断参照用のRLSポリシーを変更すること（条件はアクション側で課す）
- RLSの影響を受ける一覧取得の結果を根拠に、ファイルの削除を行うこと
- Storageの削除を確認する前にDB行を削除すること
- service-roleのキーを、ブラウザ側のコードから参照できる場所に置くこと
