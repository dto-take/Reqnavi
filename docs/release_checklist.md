# ReqNavi 本番デプロイ前チェックリスト

これまでの開発・Stagingへの反映で実際に起きた問題を踏まえて作っています。リリースのたびに更新してください。

**前提**：CLAUDE.mdの「環境について」のとおり、**本番のSupabase/Vercelには、リリース承認を経ずに接続・操作しない**。

## 1. 着手前に決めること（未決のままでは進めない）

- [ ] **Gemini APIの「学習未使用」契約条件の法務確認（TD-001）**：確認前は、機密度の高い案件データを本番に投入しない。アップロードされた顧客資料の内容がGeminiに送信される点を、顧客への説明・契約（NDA等）の観点でも確認する
- [ ] **運用・保守を担当する部門の確定（TD-002）**：障害時の一次対応、Geminiの利用枠・費用の管理、利用者からの問い合わせ窓口
- [ ] **環境の構成を決める**。現状、Vercelの「Production」（`main`ブランチ、`reqnavi.vercel.app`）は、接続先が**Stagingのデータベース**になっている。本番用のSupabase（`reqnavi-production`）に切り替えるには、次のどちらかを選ぶ必要がある
  - (a) 同じVercelプロジェクトで、Production用とPreview用の環境変数を分け、Productionを本番DB、PreviewをStaging DBに向ける。この場合、`main`へのpushが本番に直接反映されないよう、Production Branchを別のブランチ（例：`release`）に戻す
  - (b) 本番用に別のVercelプロジェクトを作る
- [ ] **契約プランの確認**：Supabase（無料プランは一定期間アクセスが無いと自動停止する。実際にStagingで起きた）、Vercel（関数の実行時間・ログ保持の上限）、Gemini（無料枠は1日20回程度しか呼べなかった）
- [ ] **本番のURL（ドメイン）とHTTPS**
- [ ] **最初の管理者アカウントを誰にするか**、およびリリース承認者の記録

## 2. 環境の分離

### Supabase（本番用プロジェクトを新規作成する）
- [ ] 本番用プロジェクトを**Stagingとは別に**作成した（Stagingのデータベースを本番として使い回さない）
- [ ] リージョンは、データの所在要件とVercelの関数リージョンを踏まえて決めた
- [ ] 本番用のProject URL・anon key・service_role keyを控えた（チャット・スクリーンショット・ログに貼らない。過去に貼ったことがある鍵は本番で使わない）

### Vercelの環境変数（本番用の値を設定する）
| 変数名 | 種別 | 注意 |
|---|---|---|
| `NEXT_PUBLIC_SUPABASE_URL` | Config | **ドメインのみ**（`https://xxxx.supabase.co`）。末尾に`/rest/v1/`を付けない（実際に起きた誤り） |
| `NEXT_PUBLIC_SUPABASE_ANON_KEY` | Config | |
| `SUPABASE_SERVICE_ROLE_KEY` | **Secret** | サーバー側のみ。`NEXT_PUBLIC_`を付けない |
| `GEMINI_API_KEY` | **Secret** | 本番用の別のキーを使う |
| `NEXT_PUBLIC_SITE_URL` | Config | 本番URL |
| `OWN_COMPANY_EMAIL_DOMAIN` | Config | 未設定だと、**すべてのGoogleログインが拒否される**（安全側の設計） |

- [ ] 上記の変数が、**Productionのスコープ**に設定されている（Previewだけに入れていない）
- [ ] `NEXT_PUBLIC_`で始まる変数は、**変更後に再デプロイしないと反映されない**（ビルド時に埋め込まれる）。値を変えた場合は再デプロイした
- [ ] 本番のURLが、StagingのSupabaseを向いていない

## 3. データベース・マイグレーション

- [ ] ローカルのマイグレーションがすべてコミットされている
- [ ] 本番に`supabase db push`し、**`Already up to date`ではなく、実際に全件が適用された**ことを確認した（マイグレーション履歴と実際のスキーマが食い違った実例あり。規約45）
- [ ] **本番では`supabase db reset --linked`を絶対に使わない**（全データが消える。Stagingでのみ許される手段）
- [ ] ローカルとリモートで、適用済みマイグレーションの一覧が一致する（`supabase migration list`）
- [ ] **1000行の上限で切り捨てられる取得が残っていない**：ベースラインはDB関数`create_baseline_snapshot()`、その他の案件全体の取得は共通の`fetchAllPages`で対応済み。新しく案件全体の行を取得する処理を足した場合は、同じ方法を使う（規約62・63）。1,100件以上の項目を持つ案件で、スナップショット件数・差分・孤立チェックの対象件数が元の件数と一致することを、リリース前に再確認する
- [ ] 公開スキーマの全テーブルでRLSが有効：
  ```sql
  select tablename from pg_tables where schemaname = 'public' and rowsecurity = false;
  ```
  結果が空であること（意図して無効にしているものがあれば、その理由を記録する）
- [ ] シードデータが入っている：自社company（固定UUID）、Salesforceの`platform_knowledge_sets`、`chapter_column_templates`、`nonfunctional_aspect_master`、`prompts`（各用途で`is_active`が1件）
- [ ] Storageのバケット`project-documents`が非公開で、1ファイル20MBの上限が設定されている。アップロード・取得・削除のポリシーがある
- [ ] **Storageに、削除済み案件の孤立ファイルが無い**（本番相当の環境で、存在しない案件のフォルダ配下にファイルが残っていないことをSQLで確認する。E2Eで、メンバーではない管理者が案件を削除するとファイルが残る不具合が見つかった。修正後も再確認する）
- [ ] **登録されていないStorageのファイルが無い**（資料の登録に失敗してファイルだけが残っていないこと。読み取り専用のSQL：`select o.name from storage.objects o left join source_documents d on d.storage_path = o.name where o.bucket_id = 'project-documents' and d.id is null;`。列名は実際のスキーマに合わせる。結果が出たら、StorageのUIから削除する）
- [ ] バックアップの有無・保持期間を、契約プランで確認した。最初の実データを入れる前に、手動でバックアップを取る手順を決めた

## 4. 認証・権限

- [ ] **Authentication → Hooks**で、`custom_access_token_hook`（JWTに`tenant_id`/`user_role`/`company_id`を入れる）を**ダッシュボードで有効化**した（マイグレーションでは設定されない）
- [ ] **URL Configuration**：Site URLが本番URL。Redirect URLsに`https://<本番URL>/auth/callback`（または`/**`）を登録した（未登録だと、ルートへ飛ばされる実例あり）
- [ ] **Googleログイン**：本番用のOAuthクライアントを作成し、リダイレクトURIに本番SupabaseのコールバックURLを設定した。Supabaseの「Providers → Google」にClient ID・Secretを設定した
- [ ] Google側の**OAuth同意画面の公開ステータス**を確認した（「テスト」のままだと、登録したテストユーザーしかログインできない。社内向けならユーザータイプ「内部」）
- [ ] 最初の管理者を作成した（Studioで認証ユーザーを作成→`user_profiles`に`admin`・テナント・自社companyを登録）。その後の追加は`/admin/users`、または自社ドメインのGoogleログイン
- [ ] **テスト用アカウントが本番に存在しない**（ローカル用の`pm-test@example.com`等）
- [ ] メール送信を使う機能がある場合のみ：Supabase既定のメール送信には送信数の制限があるため、独自SMTPの設定を検討した

## 7. 通しの動作確認シナリオ（Staging、または本番直前のリハーサル環境で）

サンプル資料（`sample-docs/`の01〜09：Markdown、PDF、Excel、PowerPoint、KPI設計資料）を使う。

**案件と資料**
- [ ] 案件を作成し、対象章を選べる
- [ ] 9ファイルを一括でドラッグ＆ドロップしてアップロードでき、PDF・Excel・PowerPointも取り込める。21MBのファイルは、アップロード前に弾かれる
- [ ] 各資料の分類タグが妥当（特にKPI設計資料に「KPI」が付く）
- [ ] **本番ビルド（Staging）で、Excel・PowerPoint・Word・PDFの資料からテキストが抽出される**（`ai_interactions`の`text_length`が0でない。分類タグが中身に基づく。11章・3章のAI素案が、Excel・PowerPointの内容に基づく項目を作る）。本番ビルドでは、ファイル形式の自動判定が失敗してテキストが取れない問題があった（規約46）

**AI素案**
- [ ] AI素案の一括生成で、1〜3章（ロードマップ含む）、5〜9章、11〜14章に項目ができる。0件の章が無い
- [ ] 4章（KPI）、10章（非機能要件）で、AI候補を生成・採用・見送りできる
- [ ] 業務フロー（As-Is／To-Be）、画面遷移図で、AI生成・差分提案を採用・見送りできる
- [ ] 同じ章で再生成しても、確定済みの項目が消えず、AI素案だけが置き換わる

**編集と確定**
- [ ] 各章のカード表示で、グループ化・フィルタ・一括確定・不採用・削除が動く
- [ ] KPI・進捗・非機能要件・画面遷移図・業務フロービルダーで、追加・編集・並べ替え・確定ができ、確定後は編集できない
- [ ] 進捗画面で、依存関係のある工程をドラッグすると、後続が追従する

**判定と出力**
- [ ] 確定判定ダッシュボード・整合性チェックの数値が、画面の実態と合う
- [ ] ベースラインを確定でき、その後の変更が差分管理に出る
- [ ] Word、PowerPoint、画面設計書（Excel）、業務手順表（CSV）をダウンロードでき、日本語のファイル名・文字が崩れない

**権限**
- [ ] admin／pm／member／partnerの各ロールで、見える範囲・できる操作が設計どおり（パートナーに非公開の項目が見えない）
- [ ] 案件トップの「最近の動き」・章の進み具合・サイドバーに、パートナーに見せない設計の項目や数値が出ていない（「最近の動き」は項目の更新日時から導出しているため、見せてはいけない項目が混ざらないことを、パートナー権限のテストユーザーで確認する）
- [ ] 管理者が、自分がメンバーではない案件を開いたとき、案件一覧・案件トップとも「メンバーではない案件のため、進捗は表示されません」と表示される（「確定 0 / 0・未着手」と誤表示されない）
- [ ] 資料の削除：`pm`・`admin`だけが削除でき、`member`・`partner`は操作が出ず、サーバー側でも拒否される。削除すると、Storageのファイルとの行がともに消え、出典の表示が「削除された資料」になり、項目の内容は残る
- [ ] 案件メンバーの削除：最後の`pm`／`admin`を外せない。外したメンバーが案件を開けなくなり、そのメンバーの項目・工数記録が残る
- [ ] **監査ログ**：資料の削除・メンバーの削除・案件の削除・ベースラインの確定で、記録がちょうど1行できる。案件の削除後も記録が残る。`admin`だけが`/admin/audit-logs`を閲覧でき、`authenticated`から書き込み・更新・削除ができない
- [ ] AI分類が失敗した資料が「未分類」で登録され、再分類できる。未分類の資料があるとき、一括生成ページに案内が出る
- [ ] Googleログイン：自社ドメインの初回（自動登録）、再ログイン、他ドメインの未登録（拒否）、他ドメインの事前登録済み（許可）
- [ ] 案件横断連携が、双方オプトインでのみ有効になる

**削除とエラー**
- [ ] 案件を削除すると、関連するテーブルの行とStorage上の資料ファイルがすべて消える（**案件のメンバーではない管理者が削除した場合も**。`project_id`を持つ全テーブルと`storage.objects`の件数を、削除前後で比較する）。案件一覧から消える
- [ ] 通信を切った状態の操作で、エラーが日本語のトーストで表示され、画面が実際の状態に戻る
- [ ] **サーバー側の拒否（ロック中、権限、入力不正、重複）の日本語の理由が、本番ビルドで、トースト・インラインに表示される**（本番ビルドでは、`throw`した例外のメッセージが消えるため。汎用のエラー画面や、英語の長文が出ない。規約67）
- [ ] **E2E報告書（2026-10-05）のMajor指摘3件（確定済み項目の直接編集、他案件参照の条件、案件削除時のStorage残存）が解消され、該当項目が再検証されている**

## 10. 受容済みの既知の制約

- 画面遷移図のノード・遷移は、`Tab`での巡回ができない（右パネルの一覧から選択できる）
- Geminiの「別の案を出す」は、一部の画面でサーバー側の完全な重複排除をしていない（直前の候補を除外リストとして渡す簡易方式）
- 見送ったAI候補をDBに記録しない画面がある（KPI・非機能要件）。画面遷移図のみ、見送りを記録して再提案しない
