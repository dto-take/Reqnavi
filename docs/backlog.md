# ReqNavi バックログ（リリース後の課題・判断待ち・受容済みの制約）

リリース前に必要なものは、`release_checklist.md`で管理する。ここには、**意図的に先送りした項目**を記録する。リリース後に着手する前に、各項目の「前提・理由」を確認すること。

---

## 1. リリース後に対応する候補

| 項目 | 前提・理由 |
|---|---|
| 変更申請の承認・クローズ | 現状は、登録と一覧表示まで。承認・クローズの画面とServer Actionが存在しない（E2Eで判明。2026-10-05） |
| 顧客の編集UI | 顧客の追加のみ。名前の修正等の手段が無い（未使用だった`updateOrganization`は削除済み）。編集が必要になったら、機能として設計する |
| 案件の複製・アーカイブ | 案件一覧の「⋯」メニュー（複製・アーカイブ・削除）は、新機能で設計が必要なため作らなかった。削除は案件設定の「危険な操作」に集約済み |
| メンバーではない管理者向けの「閲覧のみ」表示 | 管理者は、メンバーではない案件の書き込み系の画面を開けるが、操作はRLSで拒否される（画面にはエラーが出ない場合がある）。「閲覧のみです」の表示で足りる |
| 案件ごとの役割 | `project_members`に案件ごとの役割の列が無い場合の話。役割は全体の役割（`/admin/users`）のみ。案件ごとの役割は、データモデルの変更が大きいため、必要性を確認してから設計する |
| 見送ったAI候補の記録（KPI・非機能要件） | 画面遷移図は見送りを記録し再提案しないが、KPI・非機能要件は、画面上の一時的な候補で、見送りを記録しない（「別の案を出す」は、直前の候補を除外する簡易方式） |
| 削除した資料の出典の保持 | 資料を削除すると、出典（`item_sources`）の行も一緒に消える（外部キーが`ON DELETE CASCADE`）。項目の内容は残るが、どの資料から導いたかの追跡は失われる。確定済みの項目の根拠を残したい場合は、`source_id`をNULL可にして主キーを付け替え、ファイル名を控える列を足し、「削除された資料（ファイル名）」と表示する（マイグレーションが必要） |

## 3. 受容済みの制約

- 画面遷移図のノード・遷移は、`Tab`で選択できない（右パネルの一覧から選択できる）。キーボードだけでの完全な操作は対象外
- 「最近の動き」（案件トップ）は、項目の更新日時から導出しており、業務フロー・画面遷移図・進捗だけを編集した場合は反映されない。「すべての変更を見る」の遷移先（変更履歴の画面）は無い
- 案件一覧の「最終更新」も、項目の更新日時が基準
- ベースラインの確定には、充足率などの前提条件が無い（任意に確定できる）。確定判定ダッシュボードは参考情報
- 15章（進捗）は、確定の概念が無く、確定判定の対象外
- 4・10章を含まない旧基準で作られたベースラインの確定率は、含む新基準と比較できない（本番にはまだ実データが無いため、影響なし）
